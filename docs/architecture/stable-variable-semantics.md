# Стабильные имена переменных и изменение значений

Дата требований: 2026-11-03. Статус: обязательное уточнение пользователя. Заменяет противоречащие правила manual version aliases и восстановления прежних значений в [контракте 2026-10-31](secret-label-templates-contract.md) и [предложении MCP](mcp-agent-integration-design.md). На момент первоначальной записи код ещё использовал отвергнутое версионирование. Обновление 2026-11-04: исправление реализовано в исходниках; [принятые границы](mcp-implementation-contract.md), [проверки](mcp-implementation-validation.md). Действующая пользовательская БД не мигрировалась в ходе разработки.

## Требуемое поведение

| Операция | Результат |
|---|---|
| Создать `BASE_URL = a.com` | Маркер `$${<BASE_URL>}` обозначает значение переменной |
| Изменить значение на `b.com` | Имя `BASE_URL` и маркер `$${<BASE_URL>}` прежние; подставляется `b.com` |
| Изменить значение повторно | Никаких `_V_...`, случайных суффиксов или отдельной переменной для прошлой версии |
| Переименовать `BASE_URL` в `API_URL` | Доступное имя и маркер становятся `API_URL` / `$${<API_URL>}`. Сохранение работоспособности старого имени не требуется |
| Модель использовала старое имя | Совместимость старых сессий после переименования — ответственность пользователя. Агент должен свериться с актуальным Vault и выбрать существующее имя |
| Маскирование | Актуальные значения по-прежнему заменяются соответствующими переменными; переменная не является неизменяемой ссылкой на прошлый original |
| Контекст модели | Модель заранее знает о Vault; каталог является снимком и может измениться вне сессии. Последнее [уточнение о чтении по необходимости](mcp-agent-integration-spec.md#последнее-уточнение-каталог-является-снимком) развивает прежнее требование автоматически видимого списка. Автоматические переменные — по необходимости |

Почему: пользователь ожидает обычную изменяемую переменную. Цель: можно заменить адрес/пароль, сохранив все обращения к имени. Как: stable name/token → текущее значение, самостоятельная операция rename. Почему не прежнее решение: immutable mapping original→versioned alias подменял семантику переменной и сохранял отвергнутые пользователем старые значения для последующего восстановления.

## Исходный список исправлений от 2026-11-03

Ниже сохранено состояние до реализации. Принятые впоследствии решения по снимкам запроса, неизвестным токенам, повторному использованию имён и архивам находятся в контракте реализации; это решения координатора в рамках поручения, а не дополнительные цитаты пользователя.

- `VaultStore.setManualSecret` сейчас выдаёт `_V_...` при смене original; `loadFromDb` добавляет архив в inbound mappings; это не соответствует уточнению.
- UI сейчас блокирует имя редактируемой записи; API не выделяет rename. Нужен явный способ переименовать существующую переменную, а не создать вторую запись под новым key.
- При смене значения нужно пересчитывать кодированные представления, сохраняя имя основной переменной и точность URL/Base64/JSON восстановления. Конфликты с чужими именами нельзя молча перезаписывать.
- Предыдущее правило «выданный manual token никогда не обозначает другой original» больше не норматив: именно смена значения той же переменной разрешена.
- Архив прежних значений не должен применяться как механизм исполнения старого имени/маркера. Уже имеющиеся данные и backups не удалять молча; переход от ошибочно созданных `_V_...` к стабильным именам требует явного плана без потери текущих значений.
- Граница изменения во время уже выполняющегося запроса/частично пришедшего токена требует точного решения и теста. Нельзя под видом snapshot незаметно вернуть пожизненную старую семантику. Подстановка одного токена должна быть целостной.
- Детальное поведение неизвестного токена и повторного использования освобождённого имени ещё не определено пользователем; не превращать возможное поведение модели в доказанную гарантию восстановления.

## Инструкции и каталог

В инструкциях указать: необходимые пароли, адреса и другие значения могут находиться в Vault; каталог позволяет выбрать существующее имя без угадывания. Любой загруженный список — снимок, а не гарантия актуальности: изменения возможны вне текущей сессии. Если подходящей переменной нет в старом списке, имя больше не распознаётся или актуальность вызывает сомнения, перечитать каталог. Не делать вывод об отсутствии значения только по прежнему списку. Смена только значения известной переменной сохраняет имя/маркер и не требует перечитывания каталога перед каждым использованием.

Способы доставки исследованы в [MCP-предложении](mcp-agent-integration-design.md). Прежнее требование всегда видимого списка и последующее рассуждение о чтении по необходимости сохранены в [исходной спецификации](mcp-agent-integration-spec.md). Правила внешних изменений входят в автоматически загружаемые инструкции MCP; отдельный skill не требуется, если текст помещается в MCP. Выбор proxy injection либо иной автодоставки каталога не состоялся; это технические предложения, не универсальная гарантия MCP.
