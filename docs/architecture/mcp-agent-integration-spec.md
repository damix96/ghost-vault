# MCP, инструкции агента и запуск GhostVault

Дата: 2026-11-03. Источник требований: сообщения пользователя в задаче проекта. Статус: требования сохранены; техническая схема и реализация ещё не утверждены как завершённые. Связанный норматив: [master-spec.md](../master-spec.md).

Отдельно подготовлено [архитектурное предложение](mcp-agent-integration-design.md); его рекомендации не подменяют требования ниже.

## Приоритет и границы

Ближайший этап: доступ CLI-клиентов к переменным через локальный MCP, инструкции для модели, единственный автоматически запускаемый сервер и простая установка всей связки. Secret Vault с вводом человеком и защищённым хранением — будущий этап, который нужно учитывать в архитектуре сейчас. Прежняя рекомендация ассистента начать с шифрования не является текущим приоритетом пользователя.

## Требования пользователя

| Область | Требование | Граница решения |
|---|---|---|
| Клиенты и транспорт | Несколько CLI-клиентов получают постоянный доступ к MCP через localhost: `cli_N ↔ localhost ↔ MCP` | Конкретный HTTP-транспорт, адрес, порт и клиентские адаптеры ещё не выбраны |
| Каталог переменных | Инструмент позволяет модели узнать доступные переменные и выбрать, что использовать | По умолчанию фиксированные переменные; автоматические — по необходимости. Пользователь считает обращение к автоматическим маловероятным |
| Инструкции | Объясняют назначение инструмента, использование токенов и правила свежести; загружаются вместе с MCP без отдельного действия модели | Если правила помещаются в описании MCP, отдельный skill не нужен. Автоматическая видимость правил проверяется у поддерживаемых клиентов |
| Осведомлённость и свежесть | Инструкции заранее объясняют, что нужные токены, пароли, адреса и другие значения могут находиться в Vault; ранее загруженный каталог может устареть вне текущей сессии | После обсуждения автоматической доставки пользователь рассматривает чтение по необходимости. Не превращать прежний снимок в доказательство актуальности; подробности последнего уточнения ниже |
| Secret Vault, будущий этап | По запросу API или MCP человек вводит значения для одного или нескольких имён | Пример пользователя: `secret -set VAR_NAME VAR2_NAME ...`; точный CLI/API/MCP-контракт пока не определён |
| Интерфейс ввода | Открывается окно терминала и запрашивает значения по очереди | Допустимый рассматриваемый вариант — автоматически открываемая страница браузера с вводом человеком; окончательного выбора нет |
| Защищённое хранение | Введённые таким способом секреты сохраняются в системе зашифрованными средствами Windows | Windows Credentials упомянуты как возможный способ, а не выбранный API. Требуется проверить доступ фонового сервера |
| Другие ОС | Найти столь же удобное поведение для Linux/macOS | Пользователь прямо оставил механизм открытым |
| Единственный экземпляр | После перезагрузки компьютера сервер запускается один раз; последующие попытки не создают другие экземпляры | Нужны автоматический запуск и взаимное исключение; запуск до входа пользователя или при входе ещё не разграничен |
| Установка | Сервер и MCP с встроенными инструкциями должны легко и просто устанавливаться в разных окружениях | Отдельная установка/загрузка skill не требуется; формат поставки, CLI, регистрация и обновление ещё определяются |

## Последнее уточнение: каталог является снимком

Пользователь рассматривает более простое использование: модель знает о Vault из инструкций и обращается к каталогу при необходимости. В приведённом сообщении инструкции назывались skill; последующее уточнение ниже исключает необходимость отдельного skill, если текст помещается в MCP. Явное поручение — описать, что переменные могут изменяться вне текущей сессии. Ранее пользователь называл видимость списка без вызова MCP обязательной; новое сообщение развивает эту позицию в сторону чтения по необходимости. Оно не утверждает конкретный hook, proxy injection, способ автоматического обновления или период опроса.

Дословная формулировка пользователя:

> хм. ну допустим если так подумать - переменные не так часто меняются. если я например захотел сделать запрос используя авторизационный токен, я бы судя по инструкциям скила уже знал что подобные вещи скорее всего могут находиться в vault, и следующим шагом пошел бы туда смотреть. другое дело когда я ранее загрузил оттуда все переменные, и думаю что они актуальные. тут обновились они, но я уверен что у меня актуальные. это надо в инструкция прописать что эти перменные могут обновлязться мимо текущей сессии так что подобные вещи можно смотреть там.

Предлагаемый текст будущих инструкций, сформулированный ассистентом на основе этого поручения:

> Если задаче нужны авторизационный токен, пароль, адрес или другое значение, учитывай, что оно может находиться в Vault. Используй каталог, чтобы найти подходящую переменную; не придумывай её имя и не считай значение отсутствующим только по старому списку.
>
> Результат чтения каталога — снимок на момент запроса. Переменные могут добавляться, удаляться, переименовываться и изменяться вне текущей сессии. Наличие ранее загруженного списка не гарантирует его актуальность. Если подходящее имя не найдено в прежнем списке, имя перестало распознаваться или есть основания сомневаться в актуальности, перечитай каталог Vault.
>
> Используй точный токен выбранной переменной. Смена её значения сохраняет имя и токен: при подстановке используется актуальное значение. Переименование может сделать прежнее имя недоступным. Не требуется перечитывать каталог перед каждым повторным использованием известной переменной только ради возможной смены значения.

Почему: пользователь ожидает редких изменений, но не допускает уверенности модели в вечной актуальности списка. Цель: находить существующие значения и восстанавливаться после внешних изменений без обязательного запроса перед каждым использованием. Механизм: MCP-чтение каталога и явные правила свежести в инструкциях. Ограничение: текст правил сам по себе не сообщает о каждом внешнем изменении; мгновенная синхронизация потребовала бы отдельной доставки. Предложение ассистента для первого этапа — обычный MCP-каталог плюс эти правила; автоматическая доставка остаётся обсуждавшимся расширением, не выбранной реализацией.

## Инструкции встроены в MCP, отдельный skill не требуется

Последнее прямое уточнение пользователя:

> до сих пор не понял про mcp и скилл. почему это разные вещи. мне не нужен отдельный скилл если все уместится в mcp описание. отдельно грузить скилл некогда ради такой вещи которая всегда должна подгруждаться.

Актуальное требование: краткие правила доставляются вместе с MCP и видны модели заранее, без отдельной загрузки skill, чтения файла или вызова инструмента ради самих правил. Прежнее упоминание skill как обязательной части установки больше не действует при размещении правил в MCP. Если обнаружится ограничение объёма/доставки, его нужно явно обозначить; нельзя молча вернуть отдельный skill как обязательный шаг.

Предлагаемый механизм ассистента: общие постоянные правила в server `instructions`, назначение/параметры и краткие необходимые правила — в описании инструмента каталога; тексты формируются из одного исходника. Перечень переменных читается через MCP по необходимости, не встраивается динамически в эти постоянные инструкции. Модель должна знать о Vault до первого вызова, в том числе после возобновления/сжатия контекста. Поддержка такого включения — критерий проверки выбранного harness; один факт подключения MCP не доказывает видимость текста, особенно при отложенной загрузке tools.

Компактный проект server instructions:

> GhostVault предоставляет переменные для авторизационных токенов, паролей, адресов и других значений. Когда задаче нужны такие данные, проверь подходящие варианты в каталоге Vault; не придумывай имена и значения. По умолчанию каталог содержит фиксированные переменные, автоматические доступны по отдельному запросу. Используй точный токен из каталога в формате `$${<NAME>}`. Список является снимком: переменные могут изменяться вне этой сессии. Если нужного имени нет в старом списке, оно не распознаётся или актуальность вызывает сомнения, перечитай каталог. Смена значения сохраняет имя/токен и подставляет актуальное значение; переименование может сделать прежнее имя недоступным. Перед каждым повторным использованием известного имени читать каталог не требуется.

Почему: короткие правила нужны всегда, отдельная загрузка расходует шаг и может не произойти. Цель: агент заранее знает назначение Vault, синтаксис и свежесть. Как: встроенные MCP-метаданные и проверенная клиентская загрузка. Почему не отдельный skill: для этого объёма он дублирует инструкцию и создаёт ненужную зависимость. Это обновление спецификации и проект текста, не отчёт о реализации MCP.

## Совместимость с действующим протоколом

Уточнение пользователя после первого предложения: «мьютекс должен быть самым простым которые не приведет к дедлоку при краше». Две отдельные задачи: «как запустить сервер в первый раз если он не запущен, не запуская лишние команды, и как сделать так чтобы при повторном запуске, не запускалось два экземпляра?». Конкретный способ автоматического запуска ещё обсуждается; вопрос не является согласием на дополнительный ручной шаг.

После пояснения пользователь явно отверг смену маркера при изменении значения. Обязательный актуальный контракт: [стабильные переменные](stable-variable-semantics.md). Имя и основной маркер сохраняются при смене значения; переименование допускается без совместимости прежних имён. Правила входят в MCP; отдельный skill не требуется при достаточном объёме описания.

Пользователь написал сокращённо `$$<>`. Действующий формат в проекте — `$${<IDENTIFIER>}`; это разные записи, изменение грамматики пользователь не поручал. При проектировании сохранять действующий формат и использовать в инструкциях точные токены из каталога, пока отдельно не согласовано иное.

Текущее расхождение имени ручной записи и versioned wire alias — ошибка прежней реализации относительно уточнения пользователя. Требуемое поведение: `BASE_URL = a.com` → `BASE_URL = b.com` сохраняет `$${<BASE_URL>}`. Исторический [контракт версий](secret-label-templates-contract.md) больше не задаёт семантику ручных переменных.

Вывод для проектирования из назначения GhostVault, а не отдельная дословная формулировка пользователя: модель получает каталог имён, токенов и необходимых описаний, а не исходные секретные значения. Схема ответа, метаданные, фильтры и перечень доступных инструментов пока не выбраны.

## Вопросы для архитектурного решения

Новое предложение пользователя по launcher: проверить порт/API и версию; при совпадении использовать сервер; более старый остановить через shutdown и заменить; `-force` заменяет текущий; занятый неподтверждённым сервисом порт даёт `port already in use` и выход. Пользователь запросил честную оценку по 10-балльной шкале и обоснование лучшего варианта. [Оценка и дополнения](launcher-lifecycle-proposal.md) принадлежат ассистенту; они не являются уже реализованной или полностью принятой схемой.

| Вопрос | Что требуется определить |
|---|---|
| MCP | Общий endpoint и совместимость нескольких CLI; выдача фиксированных/автоматических переменных; поведение при обновлении каталога |
| Инструкции MCP | Как обеспечить автоматическую видимость встроенных правил; единый исходный текст; поддерживаемые CLI и поведение отложенной загрузки tools |
| Подстановка | В каком пути ответа токен превращается в значение; как связываются MCP-каталог, текущий alias и запрос через прокси |
| Lifecycle | Область единственного экземпляра: компьютер, пользователь или vault; конкурентный старт, аварийный выход, повторное подключение |
| Автозапуск | Запуск при загрузке ОС или после входа пользователя; работоспособность без открытого терминала/CLI |
| Secret Vault | Терминал или браузер; последовательный ввод нескольких значений; отмена; результат API/MCP без выдачи введённых значений модели |
| Хранилище ОС | Windows DPAPI/Credentials, контекст учётной записи процесса; варианты macOS/Linux; поведение заблокированного или недоступного хранилища |
| Поставка | Установка сервера и MCP с инструкциями; обнаружение установленного экземпляра; клиентские конфигурации; обновление |

Почему эти решения нужны: единый набор переменных должен быть доступен нескольким CLI без дубликатов сервера, а будущий ввод секретов зависит от пользовательской сессии и хранилища ОС. Цель: простая установка и предсказуемое использование переменных моделью. Механизм пока выбирается; нельзя считать отдельный MCP-процесс на каждый CLI, конкретный Windows API или запуск до входа пользователя уже согласованными решениями.
