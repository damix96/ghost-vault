# Запуск и замена экземпляра GhostVault

Дата: 2026-11-03. Основа — предложение пользователя: проверка порта/API и версии, reuse одинаковой версии, shutdown старой версии перед заменой, `-force`, ошибка занятого чужим сервисом порта. Дополнения ниже — оценка ассистента, не уже реализованное поведение. Заменяет рекомендацию обязательного отдельного Windows mutex в [MCP-предложении](mcp-agent-integration-design.md).

## Оценка и минимальная схема

Оценка исходной полной схемы: 8/10. Пользовательский сценарий удачен; недостаёт атомарности конкурентного старта, состояния startup, правил более нового сервера и корректного завершения/замены. Целевой вариант 10/10 для заявленных требований — та же схема с дополнениями ниже, без изменения пользовательского сценария. Это оценка проектирования, не обещание отсутствия дефектов.

| Наблюдение | Действие |
|---|---|
| Нет слушателя | Попытаться занять заданный TCP endpoint; только победитель инициализирует vault |
| Наш сервер, та же версия/сборка, ready | Использовать существующий процесс |
| Наш сервер, starting/stopping | Ограниченно ждать состояния; timeout — явная ошибка, без бесконечного ожидания |
| Наш сервер старее | Проверить совместимость состояния/данных, запросить shutdown конкретного instance ID, дождаться завершения, запустить новую версию |
| Наш сервер новее | При совместимости использовать его. Не выполнять автоматический downgrade; при несовместимости сообщить ошибку |
| `-force` | Заменить подтверждённый наш экземпляр, включая ту же версию. Не означает убить любой процесс на порту или обойти несовместимость БД |
| Порт занят, схема/идентичность не подтверждены | `Port already in use: <address>`, завершиться с ненулевым кодом. Не утверждать наверняка, что это чужой процесс: наш сервер тоже может зависнуть или отвечать по старому контракту |
| Во время старта получен `EADDRINUSE` | Другой кандидат мог выиграть гонку; повторно проверить endpoint и применить таблицу, а не сразу объявлять чужой сервис |

Версия сравнивается семантически, не строково. Предлагаемые identity-поля: `product`, `version`, `buildId`, `instanceId`, `protocolVersion`, `state`. Нужны схема ответа и проверяемая принадлежность установке/пользователю; сам JSON с названием продукта не даёт право на shutdown. Операция управления авторизована и содержит ожидаемый `instanceId`, чтобы запоздалый shutdown не остановил уже заменённый процесс.

## Атомарность через порт

Для одного фиксированного `127.0.0.1:port` отдельный mutex можно не вводить. Проверка порта отвечает, что делать; окончательное право обслуживать endpoint даёт успешный системный `bind/listen`. Не включать совместное использование listener несколькими процессами и не переключаться молча на запасной порт. [Node net](https://nodejs.org/api/net.html#serverlisten) описывает `EADDRINUSE` при уже занятом адресе.

Критичный порядок: занять listener → отдавать минимальный identity/status со `starting` → открыть vault → выставить `ready`. До ready модельный трафик и операции с vault недоступны. Listener удерживается этим же процессом весь срок владения vault; при штатной замене закрывается последним, после завершения активных операций и закрытия БД. Нельзя открыть временный «проверочный» socket, закрыть его и потом открыть сервер: это возвращает гонку.

При crash ОС освобождает TCP listener; файл-флаг удалять не требуется. Изолированная проверка на текущей Windows 2026-11-03: второй Node-процесс/listener на временном loopback-порту получил `EADDRINUSE`; после принудительного завершения владельца следующий listener занял тот же порт. Пользовательский сервер, порт 8767 и БД в проверке не участвовали. Проверка подтверждает примитив, а не готовый lifecycle приложения.

Почему: проверка HTTP и последующий запуск не атомарны. Цель: один владелец хранилища и endpoint при одновременных стартах. Как: системный listener становится границей владения до открытия данных. Почему не отдельный mutex: для строго одного заданного endpoint он дублирует уже нужный ресурс. Если впоследствии разрешены разные порты для одного vault, потребуется отдельная блокировка по vault; такую гарантию один порт не даёт.

## Замена процесса

1. Проверить готовность нового binary/dependencies и совместимость схемы до остановки рабочего экземпляра.
2. Авторизованно запросить остановку ожидаемого instance ID. Новый трафик получает понятное состояние stopping; текущие операции завершаются в ограниченное время.
3. Закрыть vault и освободить listener. Ответ на shutdown сам по себе не доказывает завершение процесса.
4. Новый экземпляр получает listener и объявляет ready после успешной инициализации. Конкурирующий launcher заново проверяет состояние и версию победителя; не повторяет слепой shutdown по устаревшему решению.
5. При неуспехе показать конкретную ошибку. Автоматический откат допустим только при совместимых данных; старый binary нельзя запускать поверх несовместимой миграции.

Автозапуск/супервизор должен ссылаться на установленную выбранную версию. Плановый shutdown не должен заставить его снова поднять старый binary и сорвать замену. `-force` намеренно прерывает доступность; последствия для RAM auto originals/последних сессий сохраняются согласно текущему контракту хранения. Точная политика принудительного завершения активных запросов пока не определена.

## Кто вызывает launcher

Проверка версии решает повторный запуск, но launcher всё равно должен кто-то вызвать. Installer запускает его сразу и регистрирует startup ОС. При command-based MCP его может автоматически вызвать клиент; при прямом HTTP это делает ОС/супервизор либо клиентский startup hook. Ручная отдельная команда перед каждым CLI не нужна; один HTTP URL без процесса/OS activation не исполняет launcher сам.

## Проверки реализации

Одновременные cold starts; crash до/после открытия БД; конфликт чужого endpoint; зависший собственный endpoint; одинаковая/более старая/более новая версия; два одновременных updater; stale instance ID; `-force` только на своём процессе; ошибка нового binary; активный SSE при shutdown; отсутствие перезапуска старой версии супервизором.
