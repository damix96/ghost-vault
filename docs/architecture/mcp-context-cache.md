# MCP-инструкции, обновление каталога и prompt cache

Дата: 2026-11-03. Статус: проверка протокола/исходников и уточнённое предложение ассистента; механизм GhostVault не реализован. Требования: [исходная спецификация](mcp-agent-integration-spec.md), [стабильные переменные](stable-variable-semantics.md). Вопрос пользователя не считается утверждением конкретного механизма.

Последующие уточнения пользователя: модель может обращаться к Vault по необходимости, зная о нём из автоматически загруженных MCP-инструкций; в правилах обязательно предупредить об изменениях вне сессии. Отдельный skill не нужен, если текст помещается в MCP; [исходная формулировка и проект встроенных правил](mcp-agent-integration-spec.md#инструкции-встроены-в-mcp-отдельный-skill-не-требуется). Нижележащие схемы автодоставки изменяемого каталога относятся к исследованным альтернативам, не к выбранной обязательной реализации. Предложение ассистента для первого этапа — MCP-каталог плюс встроенные правила свежести; сами правила должны быть видны заранее без отдельного вызова/чтения.

## Вопрос пользователя

> предлагаешь встраивать динамически в mcp instructions наши переменные? фиксированые вдруг добавятся по середине разговора? подхватит ли инструкции их? а если подхватят то что будет с cache hit? сбросится сразу же? в каком месте в разных harness находятся инструцкии? сверху промпта или снизу?

## Что гарантирует MCP

| Механизм | Подтверждённое поведение | Ограничение |
|---|---|---|
| MCP 2025 `InitializeResult.instructions` | Сервер передаёт рекомендации при инициализации; клиент может включить их в system prompt | Не обязательное место в prompt; нет стандартного `instructions_changed`, обязывающего обновить контекст |
| MCP 2026 `DiscoverResult.instructions`, `ttlMs` | Метаданные можно получить повторно; TTL описывает свежесть ответа discovery | Клиент не обязан вызывать discovery; TTL не гарантирует повторное чтение перед каждой генерацией и доставку нового текста модели |
| Resources и уведомления | Позволяют host получать обновлённые данные | Host выбирает включение в контекст; уведомление не является новым сообщением модели |

Источники: [схема MCP 2025](https://modelcontextprotocol.io/specification/2025-11-25/schema#initializeresult), [схема MCP 2026](https://modelcontextprotocol.io/specification/2026-07-28/schema#discoverresult), [resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources). Следствие: изменение Vault или серверного текста само по себе не обновляет уже сформированный запрос модели. Нужен механизм доставки следующего снимка перед следующей генерацией; уже выполняющаяся генерация задним числом не меняется.

## Влияние на кэш

Prompt cache повторно использует подходящий совпадающий префикс. Изменение раннего блока препятствует повторному использованию старого префикса, включающего это изменение и последующие токены. Неизменившаяся часть до изменения может использоваться при наличии подходящей границы и живой записи кэша. Запись переменной в Vault не очищает кэш провайдера; влияние возникает на следующем запросе с изменённым текстом. После прогрева новый префикс тоже может кэшироваться.

| Изменение | Последствие для каталога/кэша |
|---|---|
| `BASE_URL: a.com → b.com`, имя/описание прежние | Содержимое каталога не меняется; значение туда не входит. Само это изменение не меняет prompt |
| Добавление, удаление, rename, правка описания | Меняются видимые метаданные; нужен новый снимок каталога |
| Замена каталога в начальных system/tool instructions | История после изменённого места больше не совпадает со старым префиксом |
| Новое сообщение с каталогом после уже сформированной истории | Старый префикс сохраняется; новый хвост обрабатывается отдельно, с учётом правил провайдера |
| Перенос одного актуального блока в конец каждого запроса с удалением старого положения | Раннее содержимое снова меняется; это не эквивалент постоянному добавлению сообщений |

OpenAI документирует порядок rendered prefix: скрытые system instructions → tools → developer instructions → история. Anthropic описывает иерархию кэша tools → system → messages. Это порядок API/кэширования, не универсальный контракт расположения MCP-инструкций у harness. Поддержка сообщений, границ кэша и обновлений зависит от модели и провайдера. Источники: [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching), [Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

## Уточнённое предложение GhostVault

Почему: обязательный свежий каталог без решения модели вызвать tool; динамический ранний блок мешает reuse истории. Цель: доставлять актуальные имена перед генерацией и сохранять неизменный префикс. Механизм: постоянные правила отдельно; каталог — последовательность неизменяемых событий контекста. Простая замена начального блока и переписывание описаний tools хуже сохраняют кэш истории, но остаются альтернативами при приоритете простоты и редких изменениях каталога; универсальный механизм только средствами MCP не обещается.

1. Постоянные краткие правила: назначение Vault, точный синтаксис токенов, запрет выдумывать имена, использование последнего полного каталога с учётом возможного устаревания. По последнему уточнению правила встраиваются в MCP; прежнее выделение skill отменено. Автоматическая видимость правил проверяется для каждой поддерживаемой интеграции.
2. При начале контекста — полный каталог фиксированных имён/токенов/описаний без значений. После изменения видимого каталога — новый полный снимок в конце текущей истории перед следующей генерацией. Последний снимок определяет доступные имена; предыдущие снимки считаются историческими.
3. После добавления снимок остаётся на своём месте при воспроизведении истории; предыдущие сообщения не переписываются. Нет дубликата при неизменных метаданных и нет счётчика/даты, меняющихся на каждом запросе. Внутренняя ревизия каталога — метаданные доставки, не суффикс токена переменной и не версия секретного значения.
4. Host integration либо proxy adapter проверяет каталог самостоятельно. Модель не должна вызывать MCP перед каждым использованием; MCP-каталог остаётся способом явного чтения/восстановления и запроса automatic variables.
5. Для proxy до реализации нужен контракт стабильной привязки событий к сессии/ветке: полная история или `previous_response_id`, повтор запроса, reconnect, compaction, разветвление, concurrent requests. После потери/сжатия контекста — актуальный полный снимок. Не менять ID tools и не разрывать пары tool call/result; каталог передавать как данные в допустимом для протокола сообщении. Привилегия роли и физическая позиция — разные свойства.

Приёмка будущей реализации: синтетический каталог меняется в середине сессии без tool call модели; следующий запрос содержит новый снимок; неизменная история остаётся побайтно прежней; изменение только значения не меняет каталог; после compaction актуальный снимок восстановлен; измерены `cached_tokens` / `cache_read_input_tokens` на реально поддерживаемых клиентах и моделях. Сохранение префикса — условие reuse, не обещание 100% cache hit.

## Альтернативы по запросу пользователя

На этапе вопроса «какие еще вариианты есть?» пользователь ещё не выбрал механизм и не пересмотрел требование видимого каталога без вызова модели. Ниже сохранено сравнение для того этапа; более позднее рассуждение о чтении по необходимости отмечено в начале документа. Смена только значения не меняет каталог ни в одном варианте.

| Вариант | Почему / для чего | Механизм | Цена и границы |
|---|---|---|---|
| Каталог в описании одного MCP tool | Простая поставка через обычный MCP без отдельного SDK клиента | В описание `ghostvault_list_variables` включаются фиксированные имена, токены, назначения; изменение метаданных сопровождается уведомлением `tools/list_changed` | Нужно проверить повторный `tools/list` и обновление модельного контекста у выбранных клиентов. Lazy tool search может скрыть описание; лимиты могут обрезать каталог. При замене ранних tool definitions теряется reuse последующей истории; при редких изменениях это допустимый компромисс, а не технический запрет |
| MCP resource с подпиской | Каталог является данными; стандартный способ сообщать изменения | Предлагаемый URI `ghostvault://variables`; host читает и подписывается, затем автоматически доставляет обновление модели | Подписка/уведомление не гарантируют попадания в prompt. Нужен host с автоматической доставкой либо adapter; положение обновления определяет кэш |
| Нативный hook/plugin harness | Клиент владеет историей и умеет штатно добавлять контекст | Hook читает localhost-каталог и выдаёт новый снимок только при изменении; модель не вызывает tool ради списка | API и события зависят от клиента. `UserPromptSubmit` покрывает пользовательские ходы, не каждую генерацию внутри автономного цикла; нужны дополнительные события или точка перед model request. Сохранение истории и resume проверяются отдельно |
| Генерируемый файл каталога | Простая локальная поставка рядом с инструкциями | Сервер поддерживает отдельный `GHOSTVAULT.md` без значений; adapter/host загружает его как контекст | Перезапись файла не обновляет уже загруженный prompt. Без автоматического перечитывания остаётся стартовый снимок; зависимость от hook возвращает вариант выше. Пользовательские AGENTS/CLAUDE/skill-файлы целиком не перезаписываются |
| Каталог в обычных ответах Vault tools | Доставить обновление без дополнительного round trip | Когда модель уже вызывает наш MCP tool, сервер добавляет новый каталог в текст результата | До первого такого вызова обновление невидимо. Наш MCP не может менять ответы чужих tools. Это дополнительный канал, не выполнение требования постоянной видимости |
| Один явный запрос при старте/после потери контекста | Минимальная реализация и меньшая частота вызовов | Модель читает список один раз, затем повторяет по необходимости | Не соответствует строгому требованию «видеть заранее без вызова». Изменения извне могут остаться незамеченными; предлагается только как компромисс, требующий изменения требования пользователем |

Факты MCP: [tools, discovery и list_changed](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [resources и подписки](https://modelcontextprotocol.io/specification/2026-07-28/server/resources). Уведомления 2026 доставляются через соответствующую подписку `subscriptions/listen`; способ 2025 отличается, нужен согласованный SDK. Обновление каталога через metadata — предложение поверх этих механизмов, не обещание одинакового поведения любых harness. [Claude Code tool search](https://code.claude.com/docs/en/mcp#scale-with-mcp-tool-search) откладывает загрузку определений tools, поэтому описание не обязано быть видно изначально.

Проверенный пример нативной доставки: [Claude Code `additionalContext`](https://code.claude.com/docs/en/hooks#add-context-for-claude) вставляется в точке события и читается следующим запросом. `SessionStart`, `UserPromptSubmit`, `PostToolBatch` покрывают разные этапы. Вывод длиннее 10 000 символов переносится в файл с превью: большой каталог нельзя считать полностью доставленным. Пример подтверждает возможность адаптера Claude Code, не поддержку аналогичного API всеми клиентами.

Рекомендация ассистента: сравнить два кандидата на целевых harness — описание одного MCP tool для минимальной установки и нативные hooks для управляемой доставки/кэша. Proxy остаётся вариантом для клиентов, чей model traffic уже проходит через GhostVault. Выбор зависит от фактической частоты изменений метаданных, лимитов каталога, поддержки обновлений и измеренной цены cache misses; сохранение кэша не должно автоматически оправдывать более сложную архитектуру.
