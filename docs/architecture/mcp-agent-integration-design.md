# Предложение по устройству MCP и установке GhostVault

Дата: 2026-11-03. Статус: историческое архитектурное предложение ассистента; команды и API ниже отражают обсуждение на дату записи. Принятый и реализованный вариант описан в [контракте реализации](mcp-implementation-contract.md), проверки — в [отчёте](mcp-implementation-validation.md). [Требования пользователя](mcp-agent-integration-spec.md) сохраняются отдельно и имеют приоритет над этим предложением. Уточнения: [стабильные переменные](stable-variable-semantics.md), [launcher с проверкой версии](launcher-lifecycle-proposal.md).

## Одна установка и один владелец состояния

Предлагается один фоновый GhostVault на пользователя с существующим proxy, dashboard, общим VaultStore и MCP endpoint `/mcp` на loopback. Несколько CLI обращаются к этому endpoint. Краткие правила входят в MCP-метаданные; отдельный skill исключён из обязательной поставки по уточнению пользователя. Для клиента только со stdio допускается маленький мост stdio → HTTP; он не открывает БД и не создаёт собственный VaultStore.

[Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) подходит для отдельного сервера. Версию протокола и совместимость реализует официальный SDK; нельзя переносить lifecycle 2025 на 2026 без адаптации. Старые клиенты используют [совместимый HTTP-контракт 2025](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

| Решение | Почему | Для чего | Как | Почему не иначе |
|---|---|---|---|---|
| Общий сервер | Автоматические originals и последние вызовы принадлежат RAM одного процесса | Один каталог и одинаковая подстановка для всех CLI | MCP и proxy получают тот же VaultStore | Отдельный vault в каждом MCP расходится с текущим single-runtime контрактом |
| Общая установка | Пользователь просит простую установку связки | Не требовать сборки UI, установки Node и отдельной загрузки инструкций | Релизный комплект с проверенным runtime, собранными backend/UI, MCP-инструкциями и шаблонами клиентской интеграции | Репозиторий и `npm run build` остаются способом разработки, не целевым installer UX |
| Фиксированный каталог данных | Сейчас Zen выбирает БД относительно cwd | Повторный запуск находит тот же экземпляр | Стабильный пользовательский data directory и canonical path | Разные cwd не должны создавать независимые экземпляры и пустые хранилища |
| Отдельная поверхность MCP для модели | Нынешний MCP управляет кодом hooks и отдаёт последний transaction context | Каталог переменных не даёт административные права | На новом endpoint сначала только инструмент каталога; admin MCP не подключается автоматически | Публикация всех существующих hooks tools не соответствует новой задаче |

Пути текущей реализации: [stdio MCP](../../ghostvault/src/mcp/hooks-server.ts), [общий proxy](../../ghostvault/src/proxy/server.ts), [Zen startup](../../ghostvault/src/zen.ts), [DB path и runtime lease](../../ghostvault/src/vault/sqlite-db.ts).

## Каталог переменных

Предлагаемое название инструмента: `ghostvault_list_variables`. Фиксированные переменные первоначально соответствуют ручным записям Vault. Автоматические включаются только параметром; архивные версии не предлагаются как актуальные переменные.

```ts
type VariableSource = 'fixed' | 'automatic';
type ListVariablesInput = { includeAutomatic?: boolean; names?: string[] };
type VariableDescriptor = {
  name: string;
  token: string;
  description?: string;
  source: VariableSource;
};
type ListVariablesResult = {
  revision: string;
  variables: VariableDescriptor[];
};
```

`includeAutomatic` по умолчанию false. Значения, варианты кодирования originals, старые значения, примеры реального трафика и transaction context в ответ не входят. Описание — только предназначенные для модели метаданные. При большом каталоге потребуется ограниченная выдача/пагинация; она не должна выдавать незаметно неполный список как полный.

Требуемый `token` ручной переменной стабилен при изменении значения: `$${<BASE_URL>}` начинает подставлять `b.com` после смены `a.com`. Переименование меняет имя и token; сохранение старого имени не требуется. [Нынешнее версионирование в коде](../../ghostvault/src/vault/store.ts) противоречит [уточнению пользователя](stable-variable-semantics.md) и требует исправления. Модель использует актуальный каталог имён; неизвестное/переименованное имя требует обновления каталога. MCP сам не меняет произвольные shell-команды: модельный трафик должен проходить через настроенный proxy.

Почему: нужна обычная изменяемая переменная. Цель: сменить значение, не меняя ссылки на имя. Механизм: stable name/token → актуальное значение, явная проекция каталога без сериализации SecretEntry. Прежнее сохранение старого original за versioned manual alias отвергнуто пользователем.

## Доставка инструкций

Один версионированный исходный текст коротких правил в поставке: общие правила передаются в MCP server `instructions`, назначение/параметры и нужные локальные правила — в описании инструмента каталога. [Прямое уточнение пользователя](mcp-agent-integration-spec.md#инструкции-встроены-в-mcp-отдельный-skill-не-требуется): отдельный skill не нужен, если всё помещается в MCP; правила должны подгружаться автоматически. Модель знает о Vault заранее, обращается к каталогу по необходимости и учитывает изменения вне сессии. Каталог фиксированных имён/токенов/описаний формируется из Vault; ранее прочитанный список не доказывает его актуальность.

Предложение ассистента для первого этапа: обычный MCP-каталог и встроенные инструкции о поиске/свежести; автоматическая доставка каждого изменения каталога не является условием готовности базового инструмента. Автоматическая видимость постоянных правил обязательна и проверяется у поддерживаемых harness, включая resume/compaction и lazy tool loading. Модель не должна отдельно читать skill ради правил. Имена MCP tools берутся из реально настроенной интеграции, включая namespace. Альтернативы автоматической доставки каталога сохранены в [проверке harness и prompt cache](mcp-context-cache.md).

Официальный механизм MCP — server `instructions`: в [2025 InitializeResult](https://modelcontextprotocol.io/specification/2025-11-25/schema#initializeresult), в [2026 DiscoverResult](https://modelcontextprotocol.io/specification/2026-07-28/schema#discoverresult). Это рекомендации для клиента; стандарт не обязывает любой harness включать их в системный prompt или постоянно обновлять контекст модели. [Resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources) подходят для каталога и уведомлений, но способ включения в контекст выбирает host. [Prompts](https://modelcontextprotocol.io/specification/2025-11-25/server/prompts) не являются обязательным автоматически загружаемым системным сообщением. Следовательно, универсальной гарантии «любой harness, всегда, только MCP» нет.

Обсуждавшееся расширение для proxy: начальный каталог fixed variables и последующие изменения метаданных доставляются полными снимками; новый снимок добавляется после существующей истории и затем воспроизводится на том же месте. Это сохраняет префикс лучше, чем замена раннего блока. Требуются отдельные контракты сессий/веток, retry, compaction и stateful API; исходные инструкции и пары tool call/result должны сохраняться. Расширение не выбрано пользователем. Передаются только имена, markers и описания без originals; смена только значения не меняет каталог. Автоматические переменные запрашиваются отдельно.

Пример правил: «Для токенов авторизации, паролей, адресов и других значений проверь подходящие варианты в Vault. Ранее загруженный каталог может устареть: переменные меняются вне этой сессии. Если нужного имени нет в старом списке, имя не распознаётся или актуальность вызывает сомнения, перечитай каталог. Не придумывай имена. Изменение значения сохраняет токен; перечитывание перед каждым повторным использованием не требуется». Полный проект формулировки сохранён в спецификации. Каталог содержит, например, `BASE_URL — $${<BASE_URL>} — адрес сервиса`, без значения `a.com`/`b.com`.

Почему: модель должна знать о Vault заранее и не считать прежний каталог вечным. Цель: поиск имеющихся переменных и разумное повторное чтение без обязательного запроса на каждое использование. Механизм: встроенные MCP-инструкции и чтение каталога по необходимости. Это проще постоянной синхронизации, но не даёт мгновенного обнаружения внешних изменений. Проверяется фактическая видимость правил у клиента; отдельный skill не используется как условие их получения. Корректность подстановки остаётся серверным инвариантом.

## Единственный экземпляр и автозапуск

Предложение для desktop: один экземпляр на пользователя с одним default vault. Это уточнение архитектуры, а не уже согласованное толкование «один на весь компьютер». Локальный порт и credential пользователя сохраняются в закрытом конфигурационном файле; чужой процесс на ожидаемом порту не считается работающим GhostVault без проверки идентичности.

Актуальное предложение: [launcher с проверкой порта, identity и версии](launcher-lifecycle-proposal.md), на основе сценария пользователя. Для одного фиксированного endpoint достаточно получить TCP listener до открытия vault и удерживать до его закрытия. Системный `bind/listen` разрешает гонку старта; после crash порт освобождается ОС. Отдельный Windows mutex для этого режима не обязателен. Прежнее предложение обязательного named mutex заменено этой более простой схемой; другой scope нескольких портов/одного vault требует отдельного решения.

Нынешний [RuntimeLease](../../ghostvault/src/vault/runtime-lease.ts) — отдельная защита одного vault от нескольких процессов: иначе RAM auto originals различались бы. Она использует отдельный `.runtime-lock`, а не длительную транзакцию на пользовательской БД, и `busy_timeout=0`. Это описание кода, не требование применять SQLite как механизм запуска. При реализации нужно согласовать старую guard с единым входом до мутаций; сейчас код и блокировки не менялись.

Запуск без ручной команды перед CLI: installer один раз регистрирует фоновую задачу/службу, сразу запускает её и настраивает последующий автозапуск. Для запуска по требованию MCP-конфигурация клиента может содержать команду `ghostvault mcp`: CLI вызывает её сам; небольшой stdio-мост проверяет общий HTTP endpoint и, если сервер отсутствует, просит ОС запустить зарегистрированный сервер, ограниченно ждёт readiness и подключается. В Windows запуск через зарегистрированную задачу отделяет lifetime сервера от дерева CLI. Мостов может быть несколько, обслуживающий сервер и VaultStore остаются одни. Закрытие CLI закрывает его мост, не общий сервер.

Это вариант `CLI ↔ stdio-мост ↔ localhost MCP`, а не прямое HTTP-подключение. Если выбран именно `CLI ↔ HTTP MCP` без мостов, работающий сервер обеспечивает автозапуск/супервизор ОС; один URL не запускает выключенный процесс. [Стандартный stdio MCP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio) даёт штатную точку автоматического запуска команды клиентом. Вариант интеграции остаётся предложением, пользователь не выбрал мосты.

| ОС | Предлагаемый desktop startup | Хранилище будущего Secret Vault |
|---|---|---|
| Windows | Task Scheduler при входе текущего пользователя; `TASK_LOGON_INTERACTIVE_TOKEN`, `TASK_INSTANCES_IGNORE_NEW`; скрытый запуск, перезапуск после сбоя | DPAPI с областью текущего пользователя либо Windows Credential Manager |
| macOS | Пользовательский launchd LaunchAgent | Keychain Services |
| Linux desktop | Пользовательский systemd service в пользовательской сессии, где доступен session bus | Secret Service через установленный keyring |

Запуск при входе — рекомендация для браузера и пользовательского хранилища, а не обещание запуска до входа. [Windows interactive token](https://learn.microsoft.com/en-us/windows/win32/taskschd/principal-logontype) и [LaunchAgent](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html) зависят от пользовательской сессии. [IgnoreNew](https://learn.microsoft.com/en-us/windows/win32/taskschd/tasksettings-multipleinstances) подавляет повторные экземпляры задачи, но ручной запуск вне планировщика всё равно проходит описанную в launcher атомарную проверку владения endpoint.

Если нужен именно запуск до входа, нужен отдельный режим фоновой службы и политика разблокировки vault/доставки UI после входа. [Linux lingering](https://www.freedesktop.org/software/systemd/man/latest/loginctl.html) запускает user manager при boot, но сам по себе не разблокирует keyring и не создаёт графическую сессию. Этот режим и multi-user область нужно выбрать до реализации installer; незаметно менять требование нельзя.

## Будущий Secret Vault и ввод человеком

Предложение: `ghostvault_request_secrets({ names: [...] })` создаёт запрос ввода; GhostVault открывает отдельную локальную страницу и показывает имена по очереди. Значения отправляются непосредственно форме GhostVault, без MCP arguments, tool results и stdout агента. Модель получает request ID и состояние, после завершения — имена и актуальные tokens. Отмена, закрытие окна, тайм-аут, повторный запрос и недоступное хранилище имеют явные состояния; HTTP/MCP вызов не висит неограниченно.

Форма использует отдельную авторизованную браузерную сессию, CSRF/Origin проверку, одноразовое подтверждение запроса, `no-store`, отсутствие внешних ресурсов. Идентификатор запроса не даёт прав читать или записывать произвольные секреты. MCP credential разрешает запросить ввод и получить состояние, но не подать значения от имени человека и не прочитать их. Открываемый URL не содержит секретов и полномочий чтения vault.

Автоматическое открытие собственным desktop-процессом можно сделать пользовательской настройкой GhostVault. Если используется стандартный [MCP URL elicitation](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation), клиент обязан запросить согласие перед открытием; обещать принудительное открытие любым MCP-клиентом нельзя. MCP form elicitation не предназначен для паролей/API keys. Без доступного desktop запрос остаётся ожидающим; человек открывает форму сам. Терминальный ввод остаётся альтернативой и должен идти через отдельный пользовательский терминал с отключённым echo, не stdin/stdout MCP.

| Backend хранения | Свойства и границы |
|---|---|
| Windows DPAPI | Шифрованные blobs можно хранить в собственной БД. [CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) обычно привязывает их к пользователю и компьютеру; не использовать machine scope как неявный default |
| Windows Credential Manager | Хранить значения/ключ через системный API; [CredRead](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw) работает с credential set logon-сессии текущего token. Служба под другой учёткой не получает автоматически хранилище пользователя |
| macOS Keychain | [Keychain Services](https://developer.apple.com/documentation/security/keychain-services) хранит секреты в зашифрованном хранилище; права приложения и запросы доступа проверяются интеграционно |
| Linux Secret Service | [API](https://specifications.freedesktop.org/secret-service/latest-single/) относится к login-сессии; коллекция может требовать unlock. В headless окружении наличие/разблокировка не гарантированы |

Рекомендация для Windows v1 будущего vault: DPAPI user scope и зашифрованные blobs в текущем storage слое, поскольку нужны произвольные изменяемые значения; Credential Manager — альтернативный provider. На остальных desktop ОС — системное хранилище. Если provider отсутствует/заблокирован, возвращать понятное состояние без незаметного сохранения plaintext. Отдельный password-unlock provider для headless — возможный последующий режим, не обязательство текущего этапа.

Шифрование на диске не изолирует секрет от любого процесса того же пользователя: DPAPI допускает расшифрование в соответствующем контексте. Защита от облачной модели обеспечивается интерфейсами и masking; агент с произвольным локальным исполнением имеет более широкие возможности. Если требуется защита и от такого агента, нужна отдельная граница прав/брокер. Серверу всё равно потребуется plaintext в памяти для текущей подстановки.

Для новых защищённых записей должны быть пересмотрены все пути plaintext: [manual persist и архив версий](../../ghostvault/src/vault/store.ts), [dashboard API](../../ghostvault/src/proxy/dashboard-api.ts), [export](../../ghostvault/src/proxy/workspace-api.ts), hooks и диагностический контекст. «Зашифровали файл» не закрывает выдачу значений через прежние API. Политику экспорта защищённых записей требуется согласовать с существующим требованием полного экспорта; старые данные и backups автоматически не удаляются.

## Установка и критерии проверки

Целевой UX: скачать пакет своей ОС, выполнить `ghostvault setup`, выбрать найденные CLI. Setup устанавливает общий runtime, автозапуск, локальные credentials и MCP-конфигурацию; инструкции уже входят в MCP, отдельный skill не устанавливается. Изменяет только свои ключи/блоки, сохраняет прочую конфигурацию и резервную копию. Повторный setup обновляет регистрацию, не создаёт второй сервис и не перезаписывает пользовательские правки. Конкретные форматы конфигурации и поддерживаемые версии CLI проверяются перед реализацией адаптеров; обещание «любой CLI без адаптера» не даётся.

Предлагаемые дополнительные команды: `start`, `stop`, `status`, `doctor`, `mcp-bridge`; будущий ручной `secret set NAME...`. `doctor` проверяет общий сервер, идентичность vault, MCP-каталог, наличие инструкций и путь proxy без раскрытия originals. При обновлении работающие запросы дренируются; остановка уничтожает RAM auto originals и runtime sessions согласно текущей политике, поэтому не обещается прозрачный hot reload.

| Этап | Проверка результата |
|---|---|
| Каталог + MCP | Несколько независимых CLI видят один каталог; fixed по умолчанию; auto только явно; нет originals/старых версий; смена значения сохраняет имя и основной token; rename меняет имя без поддержки старого; точное восстановление форм |
| Инструкции | Встроенные MCP-правила видны модели до первого вызова Vault без загрузки skill, сохраняются/восстанавливаются при resume/compaction; модель знает о внешних изменениях, не выдумывает имена и не делает вывод об отсутствии по старому списку; перечитывает каталог по необходимости. Автодоставка каждого обновления каталога — отдельное обсуждавшееся расширение |
| Singleton | Конкурентные старты дают один обслуживающий процесс; проигравшие не мутируют БД; crash освобождает lock; чужой порт и несовместимая версия дают понятный результат |
| Установка | Чистая пользовательская установка, повторный setup, вход после reboot, закрытие CLI, восстановление после сбоя, обновление и удаление регистрации без удаления пользовательских данных |
| Будущий vault | Последовательный ввод, отмена/timeout, привязка к запросу; отсутствие originals в MCP/логах/неавторизованном API; доступ сервера к provider после login/restart; locked/unavailable provider; версии и экспорт |

Рекомендуемый порядок: общий сервер и MCP-каталог → инструкции и два проверенных клиентских адаптера → startup/setup → Secret Vault. Выбор первых CLI, startup до/после login, scope singleton и политика защищённых exports остаются открытыми решениями пользователя/проектирования, не реализацией этого документа.
