## Предложение: совместимый шаблон

Почему: capture groups уже существуют в regex engine, но теряются в callback. Для чего: читаемое имя без изменения значения, которое защищаем. Как: добавить отдельное nullable `label_template` в правило; `type` остаётся категорией. Старые правила с null сохраняют `AUTO_<TYPE>_<SUFFIX>`. Для заданного шаблона имя — нормализованный результат шаблона + `_` + suffix, без добавочного `AUTO_`. Почему не иначе: переиспользование type изменит смысл сохранённых категорий; разбор имени при восстановлении свяжет старые токены с изменяемыми правилами.

Предлагаемый контракт данных:

```ts
interface DetectionMatch {
  ruleId: string;
  type: string;
  matchedText: string;
  realValue: string;
  captures: Array<string | undefined>;
  namedCaptures: Record<string, string | undefined>;
  labelTemplate: string | null;
}
```

`matchedText = match[0]`; captures передаются из matchAll/exec без изменений. Существующее `realValue = matchedText.trim()` и фильтры оставить для совместимости старых правил, явно отразить их в preview. Сам шаблон НЕ выбирает замещаемую группу. Если требуется защищать ровно полный match, включая краевые пробелы, это отдельная явная версия semantics: не менять trim молча. Оригинал в mapping не uppercase/slugify/normalize. Существующий masking сохраняет окружающие пробелы при замене trimmed substring, однако они остаются видны провайдеру.

| Синтаксис / случай | Предложение, требуется согласование |
|---|---|
| `$1`, `$2`, `${1}` | Номер capture, начиная с 1. Максимальный непрерывный блок цифр — один номер (`$12` = группа 12). `$0` и `$&` не вводить в v1; неизвестные ссылки — ошибка сохранения. |
| `$protocol`, `${protocol}` | Короткое имя только `[A-Za-z][A-Za-z0-9]*`, underscore — разделитель; сложные имена, включая `_`, только в braces. Это делает буквальный пример `DB_HUB_$protocol_$1` однозначным. Не пытаться угадывать длиннейшее существующее имя группы. |
| `$$` | Буквальный `$` на стадии рендеринга; затем общая нормализация преобразует его в `_`, поскольку `$` не входит в грамматику имени токена. Backslash не запускает второй слой интерполяции. |
| Optional unmatched group | Заменять на `NA` как явную метку отсутствия; matched empty string остаётся пустой. Некорректный template/missing declaration — ошибка сохранения, не ошибка позднего запроса. Альтернатива: пустая строка для undefined; выбор нужно закрепить. |
| Quantified/repeated group | Последний capture по native JS RegExp semantics; не собирать список всех повторений. |
| Unicode/пунктуация/пробелы в capture | Рендерить как данные, затем uppercase, каждый символ вне `[A-Z0-9_]` → `_`. Нормализуется только label, не original. Конфликты нормализации разрешает allocator. |
| Вложенные `$` в значении группы | Вставка один раз, без рекурсивной интерполяции и без eval/replace-string special tokens. |
| Пустой итог | Сохранение заведомо пустого шаблона запрещено; runtime fallback для неудачного результата — прежний безопасный `AUTO_<TYPE>` prefix, чтобы naming не отключал защиту. |
| Длина | Предложение: prefix до 96 ASCII символов после нормализации, видимое усечение до добавления suffix; template source до 512 символов. Это новые технические лимиты для обсуждения, не существующие ограничения. |

Валидация на сохранении: Zod shape + компиляция regex с теми же `gi` + проверка declarations/groups через корректный regex parser, не regex-поиск скобок в source. Общий evaluator для runtime и preview; fixtures для optional/named/числовых групп. Ошибки 400; конфликт baseline редактора 409. Добавить поле в SQL migration, `PatternRow`, create/update/get/export, baseline optimistic concurrency, worker preview. Текущие API: `proxy/dashboard-api.ts:198`, `proxy/pattern-editor-api.ts:5`; preview сейчас отдельный цикл exec (`rule-preview-worker.ts:35`).

Правило при совпадении нескольких patterns: сохранить существующий порядок. Для одного `realValue` сохранять первый уже зарегистрированный mapping; новое правило/шаблон влияет только на новые значения. Контекстные captures в lookaround могут давать разные метки одному значению; dedup по original означает «первый mapping побеждает». Это следует сообщать в preview. Существующие токены не переименовывать; edit template не ретроактивен.

## Предложение: уникальность и неизменность mapping

Номинальное пространство нынешнего 4-символьного suffix: `36^4 = 1 679 616` вариантов на одинаковый prefix. При идеальной равномерности birthday-вероятность совпадения около 26% уже при 1000 разных значениях с одним prefix; это оценка, не характеристика качества Math.random. Более длинный CSPRNG suffix уменьшает коллизии, но гарантию даёт атомарное резервирование, а не вероятность.

Почему: check-then-insert без общей транзакции допускает гонку; разные таблицы допускают одинаковый alias; derived aliases могут поменяться при rebuild. Для чего: один выданный alias всегда обозначает один и тот же оригинал/представление. Как: отдельный общий реестр выданных aliases с `PRIMARY KEY(alias)`, owner ID и сохранённым типом представления; выдача нового mapping и резервирование всех его aliases в одной SQLite write transaction. Почему не иначе: `INSERT OR REPLACE` уничтожает прежнее значение, а два раздельных UNIQUE индекса не обеспечивают уникальность между таблицами.

1. Генерировать candidate через `node:crypto` (например 12 uppercase hex символов); повторно проверить dedup оригинала внутри `BEGIN IMMEDIATE`.
2. Резервировать base и необходимые derived aliases обычными INSERT. При unique conflict откатить попытку, выбрать новый suffix, повторить; никогда не заменять чужую запись. Разумный предел, например 16 попыток, затем явная ошибка allocation и запрет отправки немаскированного запроса. Предел — предлагаемый механизм отказа, не вероятность гарантированного успеха.
3. Commit до публикации в process cache. Все manual/create/promote/delete paths обязаны использовать тот же namespace; сохранённый alias не переназначать другому оригиналу. Для manual edit предложить новую identity или явно обозначить потерю старого восстановления.
4. Хранить выданные derived aliases, не вычислять их заново с зависимыми от текущего набора counters. Migration сначала выявляет конфликты, резервирует текущие mappings без переименования; уже потерянную историческую связь восстановить только из достоверной внешней копии. Не объявлять migration исправлением прошлых токенов автоматически.
5. Для нескольких процессов DB сериализует allocation, но локальные Maps останутся stale: нужен version/reload или authoritative lookup при inbound miss, и обновление snapshots перед outbound. Одна проверка unique constraint не обеспечивает межпроцессную доступность восстановления.

Меньший первый шаг: внутри `BEGIN IMMEDIATE` проверять обе таблицы и reserved derived aliases, INSERT вместо REPLACE, публиковать память после commit. Это устраняет базовую overwrite-гонку без объединения таблиц, но без сохранения исторических derived aliases и cache-coherence нельзя обещать полную неизменность/поддержку нескольких instances. Реестр — рекомендация для полной гарантии, не обязательный объём реализации шаблонов.

Уникальность требуется в namespace конкретного vault на весь срок восстановления выданных токенов, включая manual/auto/encoded формы. Между независимыми vault БД общего обещания нет. Для защиты от переиспользования удалённых aliases оставлять tombstone без original либо использовать неповторяемый namespace epoch; конечная случайная строка сама по себе не доказывает вечную уникальность.

## Предложение: срок хранения и риск раскрытия

| Вариант | Следствие / цена |
|---|---|
| Сохранить нынешнюю персистентность | Наименьшее изменение для шаблонов, восстановление после рестарта. Оригиналы остаются на диске; это явно против текущего выраженного предпочтения пользователя. Не принимать молча как желаемую политику. |
| Автосекреты только в памяти процесса | После restart/crash mappings исчезают. Уже выданные токены в старых диалогах и отложенных ответах не восстановятся; новое обнаружение выдаст новое имя. Manual mappings/правила могут остаться в SQLite. Требуется отдельная политика обращения с ранее сохранёнными auto_secrets. |
| Request/session scope | Нужно определить identity сессии, повторные отправки контекста, параллельные запросы, завершение streams и delayed tool responses; нынешняя глобальная dedup меняется. TTL не предлагать как согласованный. |
| RAM + удержание active mappings | Graceful shutdown можно дождаться активных вызовов; crash всё равно теряет mappings. Выжившие stream snapshots могут временно восстанавливать после удаления основной записи, поэтому deletion semantics требуется определить отдельно. |

Почему обсуждать отдельно: шаблон меняет имена новых записей; retention меняет возможность восстанавливать старые ответы. Как при volatile policy: immutable request snapshots и явная граница lifetime, никогда не переиспользовать старый alias для другого original. Почему не просто чистить при старте: это удаляет существующие данные без разрешения и ломает незавершённые/возобновлённые диалоги. Очистка mapping также не удаляет originals из transactions, exports, резервных копий и SQLite WAL; обещание «ничего не сохраняется» требует отдельной проверки всех путей записи.

Captures становятся видимыми провайдеру в alias. Группа protocol может быть приемлемыми метаданными; host/user/db/password может раскрыть сам секрет. Uppercase/sanitation не обеспечивают конфиденциальность, suffix не скрывает prefix. Рекомендация: явно показывать в preview исходные группы и итоговую отправляемую метку, предупреждать о содержимом captures; поддержать статический label как альтернативу. Запрет любых captures без решения пользователя не предлагается. Если хочется богатое локальное описание без раскрытия, отделить локальный displayLabel от opaque wire alias; это другой продуктовый вариант, не эквивалент запрошенной читаемой метке в токене.

## Рекомендация и решения до реализации

Рекомендую отдельное `label_template`, сохранение существующей грамматики токенов и старых mappings, атомарный allocator с запретом overwrite; исправление уникальности оправдано независимо от шаблонов. Политику ephemeral auto mappings обсудить явно до изменения сохранения: нынешний контракт расходится с новым предпочтением пользователя.

Требуются продуктовые решения: видимая провайдеру метка или только локальное описание; синтаксис коротких имён/escaping; missing capture `NA` или empty; нормализация/длина; сохранение первого mapping при новом template; допустимый срок восстановления после restart; судьба существующих disk mappings и истории. Не требуется разрешение на само исследование; разрешение на удаление данных этим отчётом не подразумевается.

Перед приёмкой реализации: forced collision и retry exhaustion, manual/auto/derived конфликты, два DB writers и stale cache, DB failure до commit, exact roundtrip всех представлений и chunks, restart с неизменными aliases, template edit без переназначения старых токенов, отсутствующие/пустые/repeated/Unicode captures, raw whitespace, контекстные группы, утечка capture в wire label, migration/rollback. Rollback на старый binary может проигнорировать template, а старый allocator снова нарушит registry; такой rollback нельзя объявлять безопасным без совместимой защиты записи.

Навык `backend-invariants` применим: помог отделить имя, identity, original и representation, обнаружить overwrite, потерю capture и нестабильность derived aliases. Существенного пробела для этой задачи не выявлено; project-specific синтаксис и retention оставлены в отчёте, а не перенесены в общий skill.
