## Catalog and mutable variables

2026-11-07 user correction: the public MCP projection now omits redundant `token`; it returns `{name,description?,source}`. Static instructions construct `$${<NAME>}` from the returned name. The internal `VaultStore.listVariables` contract below retains token for compatibility. [Current interface/catalog contract](interface-privacy.md) supersedes only the public projection wording below.

Agreed by vault_backend and mcp_protocol, reported under `record-mcp-catalog-contract` (2026-11-04): `VaultStore.listVariables(input?: { includeAutomatic?: boolean; names?: string[] }): { revision: string; variables: Array<{name: string; token: string; description?: string; source: 'fixed' | 'automatic'}> }`. Public Vault types: `src/vault/variable-catalog.ts` (`CatalogInput`, `CatalogVariable`, `VariableCatalogResult`). Public MCP adapter contract: `src/mcp/catalog-schema.ts` (`VaultCatalogProvider`, input/output schemas). Paths are relative to `ghostvault/`. Additional backend confirmation: `catalog-contract-record` (2026-11-04).

| Aspect | Agreed behavior |
|---|---|
| Default eligibility | Fixed/manual records with `maskInAi=true` only; excluded records must not be advertised as usable tokens |
| Automatic inclusion | `includeAutomatic=true` additionally includes eligible runtime/legacy automatic variables with `maskInAi=true`; default is false |
| Names | Optional exact, case-sensitive filter; duplicates are deduplicated, `[]` returns no variables, omission discovers the full eligible catalog; none of these filters changes revision |
| Ordering | Deterministic ASCII name sorting; source remains exposed metadata included in revision |
| Descriptions | Omit empty descriptions |
| Revision | SHA-256 of the full exposed metadata for the selected inclusion mode, before applying the names filter; neither secret values nor encoded forms enter the digest |
| Projection | Names, exact tokens, optional descriptions and source only; no original or encoded/derived representation values, traffic or administrative context |

Reason: clients need a consistent catalog snapshot without secret-dependent fingerprints or filter-dependent revisions. The revision identifies the exposed catalog in that inclusion mode, not the contents of a particular filtered response: changing only a secret value or the names filter does not change it. Metadata changes can change revision; including automatic variables changes the metadata set when eligible automatic records exist. Static MCP instructions remain unchanged by catalog updates. Real temporary-database two-client HTTP and production-runtime integration have passed; current evidence and its boundaries are recorded in [validation](mcp-implementation-validation.md).

Manual set updates name-stable token and exact representation mappings without creating a new version/archive. Old version aliases must not restore old values. Stored legacy archives are preserved as data but excluded from active restoration. Determine safe local startup normalization/migration behavior using isolated databases, including collision failure without data loss. Automatic-value semantics and wire grammar remain intact.

Coordinator decision for request `vault-contract`: retain one immutable restoration snapshot per in-flight proxy request, including streaming, to preserve its masking/restoration roundtrip atomically. An update committed after that snapshot may therefore leave that request completing with its previous value. Every subsequent request captures current committed mappings; the snapshot must never be reused across the conversation or cached across requests. This is an implementation boundary selected by the coordinator, not a user request for historical versions. Verify two simultaneous requests straddling update, full buffered/streamed completion and fresh next request. Rename follows the same in-flight boundary: a prior request can finish its captured mapping; fresh requests/catalog no longer resolve the old name.

Agreed admin rename endpoint (`vault-contract`, coordinator approval): `PATCH /api/vault/secret/:key`, body `{ name: string }`; HTTP 200 `{ success: true, secret: SecretEntry }` using the existing admin representation. HTTP 400 for invalid/empty target (allowed `[A-Z0-9_]+`), HTTP 404 if fixed source absent (automatic source must be promoted first), HTTP 409 for a conflicting name/base token/representation alias. Existing admin access guards and error envelope conventions remain. Same-name request is a no-op. Atomic rename preserves value, description, createdAt and archived rows; successful actual rename advances updatedAt. POST existing set endpoint stays compatible. Do not expose this admin mutation/SecretEntry on model MCP.

Coordinator decision `reserved-name-scope` (2026-11-04): preserve one persistent manual identity across renames; metadata-only historical base-name/form namespaces may support exact own-name reclamation, including A -> B -> A across restart. Inactive historical forms are not restoration mappings. Canonical legacy normalization may adopt an original canonical archive owner only with proven same-key provenance, atomically and without activating archived values. Never treat an encoded representation name as a base name or seize an automatic/unknown-provenance reservation.

Explicit manual reuse is allowed: delete A, then create A with a new value succeeds if no current namespace conflicts; rename A -> B, then explicitly create a separate A is also allowed under the same condition. B -> A then conflicts while the new A exists. This is a coordinator-selected completion of previously unspecified behavior, not a quotation or extra user requirement. Rationale: manual tokens identify mutable named variables; a permanent tombstone would make an apparently free user-selected name unusable without preserving any required historical restoration. A reused token deliberately denotes the newly assigned current variable in subsequent requests; existing in-flight snapshots retain their already captured mapping. Rename alone does not keep the old name active.

Reclaim only the requested recorded manual base namespace and its matching form reservations, never all past namespaces of an identity. Every base/form alias must be checked atomically against current bindings, foreign active forms and automatic or unclassified legacy reservations; fail with 409 without partial writes on a genuine conflict. A different historical manual owner alone is not a permanent exclusion when that exact namespace is inactive; the former owner may still have another current name. Keep historical records/values/aliases and their provenance intact for administrative export, which cannot depend on the current registry owner. Choose the smallest safe ownership transfer or separate current-binding implementation; do not clear the registry or introduce a reset endpoint. This supersedes the old manual delete/tombstone prohibition, not automatic-token uniqueness. If persisted metadata cannot classify a legacy reservation safely, report the bounded conflict rather than infer provenance from secret values.

Required evidence: rename-back before/after restart; delete/recreate with a different current value; A -> B plus new A plus conflicting B -> A; encoded namespace and automatic/tombstone rejection; injected transaction failure with unchanged DB/memory/catalog; archival preservation without restoration; requests straddling mutation. Earlier passing tests asserting permanent 409 after manual deletion demonstrate the old behavior and must change; they are not acceptance of this decision.

Approved ownership transfer `archive-export`: vault_backend owns the narrow archive-export caller correction in `src/proxy/workspace-api.ts` and its regression tests. Add `getArchivedRepresentations(row)` or equivalent pure helper for administrative export only: derive values from that historical row, not current live mappings selected by a reused alias. It must not allocate/reserve aliases, mutate active indexes, enable inbound restoration or expose archives through model MCP. Preserve stored historical values, aliases and timestamps. If exact historical representation aliases were not persisted, distinguish regenerated representation metadata from recorded history; never silently substitute current values as historical data.

Archive grouping key may follow an actual rename solely as administrative grouping metadata, in the same atomic transaction; existing rows/payload remain preserved and cannot become executable. Thus "preserve archived rows" means preserving records and historical payload, not requiring grouping key to remain immutable. New value edits create zero archive rows. Deleting a current variable must not silently delete existing archives. Orphan archive export follows the additive decision below (`orphan-archive-export`); no new import feature is introduced. Verify a historical row sharing the current canonical alias exports its own old value while current export/restoration uses current value; also verify rename and deletion preservation/atomic failure.

### Orphan archive export

Coordinator decision `orphan-archive-export` (2026-11-04), resolving the remaining issue documented in vault_backend-result.md: add `data.orphanedSecretVersions` to the existing administrative `/api/export` JSON. Each item uses the same archived-row shape as `data.secrets[].versions[]`, including its stored grouping `key`, original historical fields and pure `getArchivedRepresentations(row)` output. An orphan is a stored version with no current fixed/manual parent key; an automatic row is not a manual parent. Preserve current `data.secrets`, envelope `format/version`, existing groups and selected `included` semantics. This is an additive sidecar belonging to secrets, not a new independently selectable group.

| Export request | Orphan field |
|---|---|
| Default/group=all | Include all orphan rows, or `[]` |
| group=secrets without id | Include all orphan rows, or `[]` |
| groups selection containing secrets | Include all orphan rows, or `[]` |
| group=secrets with id | Do not include unrelated orphan rows; omit sidecar or return `[]`; preserve current active-object filtering and 404 for missing active object |
| Other groups/selections without secrets | Omit sidecar |

Reason: preserved archival data must remain discoverable in a full/secrets export without pretending deleted variables are active. Reintroducing orphan rows into current secrets or restoration would violate current-variable semantics; silently omitting stored history from an all-secrets export obscures retained data. This change preserves administrative scope and existing consumers. Never expose this sidecar through MCP or make it executable. Apply unchanged admin authorization/Origin protections; export must not write, allocate aliases or mutate active mappings.

Optional additive archived-row `representationMetadata: 'recorded' | 'partial'` is approved for versions/orphans if emitted with an explicit conservative meaning: recorded means a complete persisted representation-metadata snapshot is known; partial means historical metadata is absent, reconstructed or otherwise incomplete/uncertain. Do not infer completeness from current owner/alias count or regenerate guessed historical aliases. If evidence cannot establish completeness, use partial. The flag describes retained metadata, not proof a token was emitted externally. Preserve historical original/aliases/timestamps and existing raw-only behavior when metadata is missing.

Verify all/secrets/selected export, id and unrelated scopes, empty arrays, deleted parent, rename/reuse/restart and unknown history. Failed mutations keep archived rows unchanged; reading/export does not modify SQL or restoration/catalog indexes. Ownership stays with vault_backend for the narrow WorkspaceApi/export helper/tests scope. No UI redesign/import/reset feature is required.

### Shutdown of stalled upstream work

Coordinator decision `shutdown-policy` (2026-11-04), prompted by independent `qa-shutdown-review`: launcher deadlines alone are insufficient because a connected upstream can leave the server stopping indefinitely. The standard runtime must allow a default 5000 ms graceful interval from entering stopping, then cancel remaining owned network requests/streams. Keep requests that finish within grace intact; after grace terminate incomplete responses as interrupted, never as successful complete responses. This is a coordinator-selected lifecycle policy, not a quotation or a new user requirement.

Gate new work immediately; close event subscriptions and coordinate MCP close with the same shutdown phase so grace intervals do not accumulate unexpectedly. Track accepted responses/cancellation signals and ensure downstream termination cancels upstream fetch/body/stream work. Await handler and activity finalizers before closing DB; release the listener last. Cancellation must cover no upstream headers, partial buffered body and ongoing SSE/token fragments. A shortened internal test interval is allowed; the user-facing default remains 5000 ms. `stop` and replacement use this same safe shutdown path; no arbitrary PID or port-owner termination.

Timing refinement approved under `shutdown-stalled-upstream-contract`: after the shared 5000 ms grace, abort tracked request controllers and terminate unfinished accepted downstream connections while keeping the listener bound. Allow up to 2000 ms for actual handler/activity settlement. Close DB and release listener only if every DB-using operation really settled. A timeout reports shutdown failure and retains ownership; it must not mark unresolved promises complete. A later authenticated shutdown may retry after an uncooperative hook releases; clear only the failed shutdown-attempt state, keep admission gated, and preserve idempotence/concurrency of cleanup. The total graceful-plus-settlement policy is 7000 ms before normal synchronous cleanup, not two independent full grace intervals for MCP and proxy.

Explicit narrow ownership extension: lifecycle_setup may change `src/proxy/stream-relay.ts` only to add an optional request AbortSignal, cancel its backpressure/drain wait on request abort and check cancellation after awaited stream hooks before continuing processing. Preserve the existing default behavior for callers without that signal. Cancellation checks do not detach or claim to cancel a hook promise that has not settled. Coordinate the public signature with its caller and test owners; leave token transformation, buffering, encoding and response semantics unchanged. The runtime's per-request signal must reach this wait so a disconnected socket cannot retain the old 30-second backpressure delay during shutdown. Relevant stream/transport regressions must pass.

This bounds ordinary cooperative network work, not arbitrary user JavaScript. An externally supplied custom hook that never settles or ignores cancellation cannot be made safe by abandoning its promise: it may later access Vault. Retain DB/listener ownership and report failure by the settlement boundary in that unsupported case; launcher readiness/stop deadlines still apply. Keep the limitation explicit; do not close DB underneath a handler or kill an embedding host process. Lifecycle must report any built-in operation that prevents the standard runtime from reaching cleanup after cancellation. Changes outside the scopes above require a direct ownership agreement.

Acceptance requires real local TCP tests on Node 22.13: normal completion within grace, no headers, partial buffered response, endless SSE and partial token, backpressure cancellation, client disconnect, repeated/concurrent stop/force, persisted-value restart, and port/DB ordering. Test a noncooperative hook separately: bounded failure keeps DB/listener, work remains gated, release followed by authenticated retry completes cleanup exactly once. Stalled network fixtures must not release upstream or abort the downstream client to make shutdown succeed. These cases passed both coordinator and independent QA; the exact installed npm artifact was reconciled with independently exercised output, as recorded in [validation](mcp-implementation-validation.md).

Windows user-login autostart is the current implementation boundary, not boot-before-login or a crash-restart supervisor. Task Scheduler was an earlier implementation option, not a user-mandated mechanism. A per-user Startup entry is acceptable; launcher ensure-start still owns singleton and first-use recovery. Preview by default and explicit apply/target remain required. Tests use temporary Startup/config directories; no real registration or enabling OS components during development. macOS/Linux automatic registration may return an explicit unsupported error in this first Windows milestone; portable start/stdio paths remain available, but cross-platform installation is not thereby accepted as complete.

Delivered Windows mechanism: per-user Startup `.lnk` plus a content-addressed PowerShell helper; hidden launch, execution-policy probe without policy changes, explicit apply. Tests exercise actual shortcut launch in temporary directories with spaces and special characters; no real registration was made. Runtime-record publication retries Windows EPERM/EBUSY/EACCES atomic rename for at most one second while retaining the listener; no unlink gap. Cancellation waits for pending publication before releasing ownership. This prevents discovery readers from causing spurious startup failures. The discovery record is not a lock: stale files cannot retain OS listener ownership after a crash.
