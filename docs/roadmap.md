Охват: отсутствие нужного компонента и его жизненный цикл; композиция/варианты и отличие повторного использования от копии реализации; совместимое расширение; обязанности автора и потребителя; доступные взаимодействия; стили/токены; тестирование/ревью и рецепты агентов. Технические решения и ограничения поддерживает архитектор в `docs/ui-kit/delivery/decisions.md`; документолог не подменяет их своим выбором и не считает наличие пакета доказательством browser-поведения.

Требование пользователя к документации: ориентир не более ~200 строк в файле; темы и ссылки для выборочного чтения; вложенность только по необходимости; `index.md` каждой папки образует дерево оглавлений. Фиксированная карта пяти файлов не была принята. Результаты документационной и delivery-проверки относятся к указанным в отчётах областям, а не полной проверке runtime/UX.

Границы завершённого изолированного этапа: код и зависимости только самостоятельного kit; перенос приложения тогда не входил в задачу. Теперь он явно разрешён отдельным этапом ниже; это не разрешение publish. Документолог не редактирует поддеревья архитектора параллельно. Доставка kit не является приёмкой текущего UI приложения.

Почему: общий kit без правил использования не предотвращает несовместимые расширения и повторение UX-дефектов. Для чего: проверить полноту требований до кода, дать агенту выборочно читать нужную тему и не смешать текущие исправления с миграцией. Как: принятый план → полные правила архитектора в тематическом дереве → отдельная проверка → решение о реализации. Почему не иначе: преждевременный код закрепляет непроверенные договорённости, крупный единый текст требует лишнего чтения, внедрение в основной frontend без отдельного разрешения расширяет изолированную задачу. Документолог не дублирует авторство и не перехватывает поддерево архитектора.

## Согласованный этап UX и последних вызовов (2026-10-25)

Статус: требования зафиксированы; навигация технически доставлена, узкая контекстная коррекция доставлена для ручного просмотра, общий UX не принят. Хранение в памяти, бюджет 200 МБ и экспорт ещё не реализованы; остальные пункты не объявлены выполненными. Источники: [master-spec.md, §6 и §9–10](./master-spec.md), [канонический UX-гайд](./frontend-ux-guide.md), [модель Vault и мониторинга](./vault-and-monitoring.md). Этот этап заменяет прежние требования постоянного журнала вызовов и сессионного TTL Auto Vault; старые отчёты остаются историческими.

| Работа | Результат и границы проверки |
|---|---|
| Последний вызов | Только последний вызов каждой сессии в памяти; полный доступный контекст до/после защиты и итоговый ответ для CLI; после рестарта runtime исчезает, конфигурация и секреты сохраняются |
| Бюджет данных | По master-spec, §6.2: 200 МБ, целиком вытесняются наиболее давно неактивные сессии; активная и единственная оставшаяся защищены; превышение не обрезает контекст и не прерывает запрос/стрим |
| Мониторинг | Сохранить удобную структуру диалогов, общий переключатель сторон; system/tools/results и неизвестные блоки не теряются; нет склейки истории вызовов |
| Секреты вызова | Уникальные ключи и вхождения в отправленном содержимом только последнего вызова; inbound отдельно; текущий `count` не выдаётся за точное число замен |
| Базовое управление | Просмотр/добавление правил в простом режиме; ввод названия секрета сохраняет каретку и выделение |
| Подсказки | Общий доступный hint/popup, понятные подписи и направления; вернуть подсказки подстановок, включая JSON/URL/Base64 |
| Экспорт | Одна настройка/запись, группа и вся конфигурация; версия формата, необходимые реальные значения, понятный состав; без runtime-диалогов и без импорта |

До реализации определить способ учёта объёма, выбор последнего при параллельных вызовах одной сессии и конкретную схему экспорта. Очистка ранее записанной истории SQLite — отдельное решение; текущая фиксация не разрешает удаление пользовательских данных. Кодовые и браузерные проверки этих изменений ещё не выполнялись.

## Текущее состояние (2026-10-24)

Актуальная оценка безопасности и приоритеты: [аудит реализации и защиты секретов](./security-implementation-audit.md). Текущие успешные функциональные тесты не означают готовность к работе с реальными паролями.

Следующий согласованный этап реализован как [фиксированные адаптеры форматов](./protocol-formats.md): Chat Completions, Responses, Anthropic, Gemini/Antigravity. Целевые поля обрабатываются после разбора JSON, manual имеет приоритет над auto; конструктор неизвестных схем не добавлялся. Проверки протоколов включены в общий `npm test`.

Добавлен [отдельный реальный провайдер Zen](./zen-cloud-setup.md), текущий gateway на 8767, отдельно от mock-стенда на 8766 и прежнего gateway на 8765. Исправлены привязка авторизации и отправка upstream: локальный OpenCode plugin регистрирует только `ghostvault-zen` с существующей Console connection и optional native relay, без копирования ключа. `ghostvault-zen/big-pickle` прошёл реальный cloud smoke через GhostVault: HTTP 200, alias вместо исходного canary в outbound, восстановление кавычек/backslash/newline/Unicode в ответе. Native transport включён только для нового Zen provider; обычные маршруты/Go сохранены. Сборка и все 10 suites прошли. Точная причина разных отказов Node/Bun в Zen не установлена; полная готовность остальных функций этим smoke не заявляется.

OpenCode обновлён до `v2.1.4`: новый `ghostvault-zen` использует native V2 config, CLI/E2E автоматически выбирает V1/V2 команды. Модель `deepseek-v4.1-flash-free` есть в обоих каталогах; реальный V2-запрос через proxy получил 403/429 от Zen, без успешной генерации.

### Локальная проверка

```powershell
cd ghostvault
npm run build
npm run demo
```

Дашборд стенда: `http://127.0.0.1:8766/dashboard?route=custom-ghostvault-test`. Mock модели: `127.0.0.1:9098`; тестовый сервис: `127.0.0.1:9099`. Остановка уничтожает данные стенда. Конфигурация нового провайдера записывается только в `e2e-sandbox/opencode.json`; раннер не изменяет глобальную конфигурацию OpenCode.

Из отдельного терминала в `e2e-sandbox`:

```powershell
opencode run --pure --model ghostvault-test/zen-mock --auto "Fetch test balance"
```

Для автоматического E2E остановить постоянный стенд (`Ctrl+C`), затем выполнить `npm run test:e2e` из `ghostvault`. Для модульных тестов использовать `$env:GHOSTVAULT_DB_PATH = ':memory:'` перед `npm test`, чтобы не записывать фикстуры в пользовательскую БД.

| SSE-парсинг стримов | `eventsource-parser` | Событийно-ориентированный потоковый парсинг Server-Sent Events без буферизации всего ответа |
| Поиск подстрок | `aho-corasick-node` | Многошаблонный поиск O(N) по предвычисленному словарю секретов за один проход текста |
| Валидация схем | `zod` | Декларативная статическая и рантайм-типизация входных и конфигурационных структур |
| База данных | `better-sqlite3` | Синхронная транзакционная работа без оверхеда промисов, поддержка режима WAL |
| GUI Подтверждения | PowerShell STA (`-STA`) + WPF | Нативный рендеринг в Windows без зависимостей от Electron / Chromium |
| Web Dashboard | Tailwind CSS + Lucide Icons | Легковесный веб-интерфейс на локальном порту без сборщиков в рантайме |

## Этапы реализации

### Этап 1: Хранилище Vault и Быстрый Детектор
1. Реализация `formats.ts`: вычисление 4 представлений секрета (`raw`, `urlEncoded`, `jsonEscaped`, `base64`).
2. Реализация `store.ts` и `db.ts`: персистентное сохранение записей `SecretEntry` в SQLite (`~/.ghostvault/vault.db`).
3. Подключение `aho-corasick-node` в `matcher.ts` для потокового выявления совпадений по правилу Longest Match First.

### Этап 2: Обратимый LLM Reverse Proxy
1. Запуск Fastify HTTP-сервера на порту `127.0.0.1:8765`.
2. Маршрут `POST /v1/messages` (Anthropic):
   - Исходящая замена: `Real -> $${<NAME>}` в теле JSON.
   - Проксирование в `https://api.anthropic.com`.
   - Прием SSE-потока: парсинг через `eventsource-parser`, пропуск через `SlidingBuffer` для сохранения задержки первого байта (TTFB 40–50 мс).
   - Перехват `tool_use`: демаскирование `$${<NAME>} -> Real` в аргументах команд перед передачей CLI-агенту.
3. Маршрут `POST /v1/chat/completions` (OpenAI): симметричная обработка вызовов `tools`.

### Этап 3: Пайплайн минимизации данных (Cache-Inspect-Get)
1. Реализация изоляции вывода инструментов в локальные файлы `.raw`.
2. Реализация `inspector.ts`: генерация схемы структуры данных без раскрытия скаляров.
3. Реализация `json-unpacker.ts`: детектирование сериализованных JSON-строк и построение виртуальных свойств `__as_json`.
4. Реализация селекторов `grep`, `slice`, `head`, `tail` для текстовых логов.

### Этап 4: GUI-мост и MCP-адаптер
1. Реализация `gui/bridge.ts`: создание, запуск и удаление задачи `GhostVaultPopup` через `schtasks`.
2. Реализация `mcp/adapter.ts`: stdio-клиент для регистрации в Claude Code, Antigravity, Cursor.
3. Локальный Web Dashboard (`http://127.0.0.1:8765/dashboard`) для мониторинга сессий и закрепления псевдонимов.
