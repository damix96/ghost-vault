# Переиспользование и совместимые изменения

[Раздел](index.md).

Почему: копии общего поведения расходятся, но искусственное объединение независимых workflows создаёт связанность. Цель — один устойчивый контракт там, где ответственность общая, без god-component.

## Выбор

1. Найти существующий компонент и прочитать ограничения.
2. Если задача выражается API — использовать его. Повтор вызова с другими данными не является копией реализации.
3. Если отличается окружение/порядок блоков — проверить композицию общих primitives.
4. Если отличается одно ортогональное состояние/оформление — оценить opt-in параметр/variant.
5. Если появились иные keyboard/value/lifecycle semantics — рассмотреть новый компонент или версию.
6. Перед зависимым кодом согласовать контракт с владельцем; не создавать локальную копию как молчаливый обход.

Общие Field/Actions у редакторов правил и подключений полезны. Их разные validation/save lifecycles не требуют универсального DynamicEditor с десятками flags. Slots/render hooks допустимы при ясном типе/семантике; произвольный bag HTML/attrs/styles не заменяет API design.

## Проверка общего контракта

Сравнить ответственность, состояния, события и причины будущих изменений. Похожий цвет или две одинаковые строки не достаточны для extraction. Для shared structure/style/behavior предпочтительна canonical реализация; новое имя файла не оправдывает fork.

Самостоятельная orchestration или временная v1/v2 coexistence возможны как обоснованное решение владельцев: причина, альтернативы, consumers, scope, проверки, условие удаления. Срочность одна не является причиной. Новый global registry/runtime/JSON UI language ради gap не вводить.

## Расширение

- Классифицировать additive, behavioral или breaking. Смена default/event timing может быть breaking без изменения типа.
- Найти затронутых потребителей через публичный API; не исследовать всю чужую реализацию вместо вопроса владельцу.
- Новый режим делать opt-in, если нет принятого breaking перехода; сохранить старые defaults/semantics.
- Проверить старые и новые сценарии, включая CSS tokens/hooks, focus и reset.
- Версию, deprecation и removal записать до релиза; указать replacement, владельца переноса и завершение поддержки.
- Релиз можно откатить как комплект [артефактов](../delivery/packaging.md); silent monkey patch/private selectors у consumer не являются rollback.

Legacy cleanup: inventory копий→canonical target→совместимое расширение→разрешённый перенос consumers→удаление старых exports/styles/examples→проверка. Полный перенос приложения уже отдельно поручен его frontend-владельцу; это не передача приложения kit owner.
