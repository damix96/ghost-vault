# 03. Кеш-пайплайн и минимизация данных (Cache-Inspect-Get)

Архитектура трехэтапного пайплайна изоляции данных, предотвращение Overfetching и парсинг вложенного JSON (`__as_json`).

## Проблема Overfetching в агентных средах

Прямой возврат вывода инфраструктурных инструментов (HashiCorp Vault, Kubernetes API, SQL-клиенты, облачные SDK) в контекст LLM создает три критических риска:

| Риск | Механизм возникновения | Последствие |
|---|---|---|
| Утечка соседних секретов | Чтение одного ключа возвращает родительский узел со всеми сертификатами, токенами и паролями окружения | Случайная передача закрытых ключей шифрования в облачный API |
| Деградация контекстного окна | Ответы размером 50–500 КБ передаются в `tool_result` целиком | Превышение лимита токенов, кратный рост стоимости запроса, вытеснение системных инструкций |
| Срабатывание внешних DLP-фильтров | Наличие конфиденциальных данных в соседних, не запрошенных полях JSON | Блокировка всей сессии на сетевом шлюзе компании |

## Архитектура: Cache-Inspect-Get Pipeline

Вместо прямой передачи сырого ответа инструмента в контекст LLM процесс изолируется на три фазы:

```
[ LLM ] ──► 1. cache_run(tool: "vault_read", path: "secret/db")
                 │
                 ▼
         ┌──────────────────────────────────────┐
         │     Изоляция в локальный кеш         │
         │     ~/.ghostvault/cache/req_89f1.raw │
         └──────────────────┬───────────────────┘
                            │
                            ▼
[ LLM ] ◄── Ответ: { "cache_id": "req_89f1", "bytes": 49152, "format": "json" }
(В контекст модели не попало ни одного байта секретов)
```

```
[ LLM ] ──► 2. cache_inspect(cache_id: "req_89f1")
                 │
                 ▼
         ┌──────────────────────────────────────┐
         │       Синтаксический AST-сканер      │
         │   • Удаляет все скалярные значения   │
         │   • Строит схему типов структуры     │
         │   • Обнаруживает сериализованный JSON│
         └──────────────────┬───────────────────┘
                            │
                            ▼
[ LLM ] ◄── Ответ: Дерево типов (структурная схема без значений)
```

```
[ LLM ] ──► 3. cache_get(cache_id: "req_89f1", path: "data.credentials.password")
                 │
                 ▼
         ┌──────────────────────────────────────┐
         │   Извлечение точечного значения      │
         │   + Маскирование через VaultStore    │
         └──────────────────┬───────────────────┘
                            │
                            ▼
[ LLM ] ◄── Ответ: "$${<DB_PASSWORD>}" (или минимальное запрошенное значение)
```

### Спецификация интерфейсов пайплайна

```typescript
interface CacheRunResult {
  cache_id: string;
  bytes: number;
  format: 'json' | 'yaml' | 'text';
}

interface CacheInspectResult {
  cache_id: string;
  format: 'json' | 'yaml' | 'text';
  schema?: Record<string, unknown>;
  linesCount?: number;
  detectedPatterns?: string[];
}

interface CacheGetParams {
  cache_id: string;
  path?: string;
  grep?: string;
  slice?: { start: number; end: number };
  head?: number;
  tail?: number;
}
```

## Распаковка JSON внутри строковых полей (`__as_json`)

В конфигурациях (Kubernetes ConfigMap, Vault KV v2, AWS Secrets Manager) частым паттерном является сериализация JSON внутри строкового свойства:

```json
{
  "request_id": "req-981",
  "config_payload": "{\"host\":\"internal.bank.kz\",\"port\":5432,\"pool_size\":10}"
}
```

### Механизм генерации виртуальной схемы

AST-сканер проверяет строковые узлы валидатором JSON. При успешном парсинге рядом с исходным полем синтезируется виртуальная типизированная ветка `fieldName__as_json`:

```json
{
  "request_id": "string",
  "config_payload": "string (json-serialized)",
  "config_payload__as_json": {
    "host": "string",
    "port": "number",
    "pool_size": "number"
  }
}
```

### Точечная адресация модели

Модель обращается напрямую к виртуальному пути:

```json
{
  "cache_id": "req_89f1",
  "path": "config_payload__as_json.port"
}
```

Демон извлекает родительскую строку `config_payload`, выполняет JSON-десериализацию в памяти, достает целевое свойство и возвращает значение `5432`.

## Обработка неструктурированных данных (Текстовые логи)

При получении сырого текста (вывод компиляторов, stdout cURL, системные логи):

1. **Фаза Inspect:**
   - Вычисление объема: количество строк, байт.
   - Детекция сигнатур по регулярным выражениям: `ISO_TIMESTAMP`, `HTTP_STATUS_CODE`, `IPV4_ADDRESS`, `ERROR_LEVEL`.
2. **Фаза Get:** Выборка данных через селекторы без загрязнения контекста:
   - `grep`: фильтрация по подстроке или регулярному выражению (`grep: "FATAL|ERROR"`).
   - `slice`: точный диапазон строк (`start: 120, end: 140`).
   - `head` / `tail`: первые или последние N строк потока.
