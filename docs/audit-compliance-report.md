## 4. Архитектурный аудит подсистем

### 4.1. Персистентное хранилище SQLite и WAL-режим

- **ПОЧЕМУ:** Атомарность транзакций, выживание базы между перезапусками CLI, поддержка параллельного чтения веб-дашбордом во время синхронного проксирования запросов агентов.
- **ДЛЯ ЧЕГО:** Гарантия нулевой потери сохраненных псевдонимов и истории перехватов при падении или перезапуске процесса GhostVault.
- **КАК:** Использование нативного движка Node.js `node:sqlite` (`DatabaseSync`) без сторонних C++ бинарных модулей. Файл базы данных размещен по стандарту спецификации в `~/.ghostvault/vault.db` (с возможностью переопределения через `GHOSTVAULT_DB_PATH`). При создании инстанса выполняется `PRAGMA journal_mode = WAL;`.
- **ПОЧЕМУ НЕ ИНАЧЕ:** Хранение в памяти (`in-memory`) уничтожает состояние при перезапуске CLI-сессии. Хранение в плоских JSON-файлах уязвимо к гонкам записи при стриминге и блокировкам файловой системы на Windows.

### 4.2. Движок авто-отлова (Pattern Engine) и промоушен секретов

- **ПОЧЕМУ:** Пользователи не объявляют каждый внутренний адрес или токен вручную; агент считывает конфигурационные файлы и репозитории, в которых содержатся чувствительные параметры.
- **ДЛЯ ЧЕГО:** Предотвращение случайной утечки неразмеченных конфиденциальных данных в сторону провайдера LLM в режиме нулевого ручного вмешательства.
- **КАК:** Класс `PatternEngine` компилирует активные регулярные выражения из таблицы `patterns` (`pat_internal_urls`, `pat_database_uri`, `pat_private_ip`, `pat_api_keys`). На вызове `scanAndAutoDetect()` входящий текст сканируется, совпадения сохраняются в таблицу `auto_secrets` со счетчиком `hit_count`, временными метками `first_seen_at` и `last_seen_at`. Метод `VaultStore.promote(key)` переносит авто-секрет в постоянную таблицу `secrets` в 1 клик.
- **ПОЧЕМУ НЕ ИНАЧЕ:** Автоматическое превращение всего подозрительного в постоянные правила засоряет хранилище мусорными строками. Разделение на `auto_secrets` (временные динамические псевдонимы) и `secrets` (постоянные промоутированные правила) сохраняет порядок в конфигурации.

### 4.3. Прозрачная маршрутизация (RouteRegistry)

- **ПОЧЕМУ:** Разные инструменты (OpenCode, Claude Code, Cursor, Aider, Ollama) отправляют запросы на разные URL-префиксы и требуют разных форматов эндпоинтов.
- **ДЛЯ ЧЕГО:** Реализация прозрачной философии: "Шлешь СЮДА ➔ GhostVault пересылает ВОТ СЮДА", исключая необходимость менять код внешних тулов.
- **КАК:** Класс `RouteRegistry` предоставляет динамические маршруты:
  - `opencode` (`http://127.0.0.1:8765/opencode/v1` ➔ `https://api.opencode.ai`)
  - `anthropic` (`http://127.0.0.1:8765/anthropic` ➔ `https://api.anthropic.com`)
  - `openai` (`http://127.0.0.1:8765/openai/v1` ➔ `https://api.openai.com`)
  - `ollama` (`http://127.0.0.1:8765/ollama/v1` ➔ `http://127.0.0.1:11434`)
  - Пользовательские кастомные маршруты (`/api/routes` POST/PUT/DELETE) с проверкой формата префикса.
- **ПОЧЕМУ НЕ ИНАЧЕ:** Жесткий хардкод апстрима ломает мультимодельные пайплайны и препятствует работе с локальными vLLM/Ollama моделями.

### 4.4. Live Inspector и эргономика UI

- **ПОЧЕМУ:** Огромные сырые JSON-логи ("простыни") перегружают оператора и скрывают факт утечки конкретного секрета среди тысяч строк контекста.
- **ДЛЯ ЧЕГО:** Мгновенный визуальный контроль подмены: оператор за 1 секунду видит, что конкретно было замаскировано и как выглядит ответ модели.
- **КАК:**
  - Автоматический фокус на последнем шаге сессии (`selectedStepIndex = Math.max(0, steps.length - 1)`).
  - Умные сниппеты совпадений (`extractSnippets(text, terms, 70)`): показ фрагментов текста с окном в ±70 символов вокруг найденных токенов вместо полного вывода.
  - Интерактивные токены с тултипом `Было в вашей консоли: "..." ➔ Ушло на сервер: "$${<...>}"` и копированием по клику.
  - Переключатель режимов: "Сниппеты совпадений" / "Полный текст" / "Исходный ввод из консоли".
  - Боковая панель управления сессиями с поддержкой индивидуального удаления сессий и полной очистки базы сессий.
- **ПОЧЕМУ НЕ ИНАЧЕ:** Полный дамп запроса объемом 100 КБ блокирует DOM браузера при рендеринге и снижает скорость реакции администратора.

### 4.5. Статус Hook Workbench в навигации

- **ПОЧЕМУ:** Компонент Hook Workbench находится в стадии внутренней стабилизации и не должен перегружать основной пользовательский интерфейс шлюза.
- **ДЛЯ ЧЕГО:** Сохранение фокуса пользователя на основном сценарии защиты секретов в CLI.
- **КАК:** В `public/index.html` кнопка `navWorkbenchBtn` исключена из навигационного заголовка. В активном меню присутствуют строго 3 раздела: Live Inspector, Secrets & Patterns, Audit Feed. При этом кодовая база `public/workbench.js` и бэкенд `src/mcp/hooks-server.ts` сохранены в рабочем состоянии для тестов и интеграции через MCP.

## 6. Итоговое заключение

1. **Инженерный стиль:** Архитектура проекта на 100% соответствует требованиям документа `engineering-style.md`. Во всей кодовой базе содержится строго **0 комментариев**, **0 старых `function` деклараций**, **0 нарушений лимита 10–300 строк**, все классы инкапсулируют состояние через стрелочные методы с неявным возвратом.
2. **Работоспособность:** Проект успешно компилируется (`tsc`), проходит 100% автоматических тестов (5 из 5 тестовых сьютов + сквозной E2E-тест), шлюз стабильно функционирует на порту 8765.
3. **Архитектура:** Полноценно функционирует персистентность в SQLite с WAL (`~/.ghostvault/vault.db`), прозрачная маршрутизация ("Шлешь сюда ➔ Пересылаем вот сюда"), PatternEngine с авто-отловом и 1-click промоушеном, а также Live Inspector без простыней с мгновенными hover-подсказками и управлением сессиями.
4. **Устранение дефектов:** Выявленные остаточные банковские заглушки (F-001, F-002) немедленно устранены в ходе аудита, сборка и тесты перепроверены и завершены со статусом PASS.
