## 2. Контекст архитектурных решений

### 2.1 Персистентность SQLite в режиме WAL
- **ПОЧЕМУ:** Хранение конфиденциальных данных и истории транзакций исключительно в оперативной памяти приводило к сбросу настроек и потере журнала аудита при перезапуске процесса или сбоях ОС.
- **ДЛЯ ЧЕГО:** Гарантия долговечности состояния масок, пользовательских паттернов и сессий CLI-агентов между запусками GhostVault без необходимости развертывания внешних СУБД.
- **КАК:** Использован встроенный движок Node.js `node:sqlite` (`DatabaseSync`), создающий файл `~/.ghostvault/vault.db` с включенным режимом Write-Ahead Logging (`PRAGMA journal_mode = WAL`) и созданием таблиц `secrets`, `auto_secrets`, `patterns`, `sessions`, `transactions`.
- **ПОЧЕМУ НЕ ИНАЧЕ:** Внешние зависимости (например, `better-sqlite3` с компиляцией нативных бинарников через node-gyp) вызывают проблемы сборки в Windows-окружении, а хранение в JSON-файлах не обеспечивает транзакционность при параллельных потоковых запросах SSE.

### 2.2 Движок предиктивного маскирования PatternEngine
- **ПОЧЕМУ:** Ручное добавление каждого адреса и ключа в хранилище требует предварительного знания всех конфиденциальных переменных, что невозможно при работе автономных агентов с динамической инфраструктурой.
- **ДЛЯ ЧЕГО:** Автоматический перехват неизвестных внутренних хостов, портов, приватных IP-сетей и токенов до того, как они покинут защищенный сетевой периметр.
- **КАК:** `PatternEngine` компилирует набор системных и пользовательских регулярных выражений:
  1. `internal-urls`: внутренние домены (`.internal`, `.corp`, `.lan`, `.local`, `localhost`).
  2. `database-uri`: строки подключения БД (`postgres://`, `mysql://`, `redis://`, `mongodb://`).
  3. `api-keys`: токены стандартизированного формата (`sk-...`, `ghp_...`, `AKIA...`).
  4. `private-ip`: приватные IPv4 адреса (10.x, 192.168.x, 172.16-31.x) с опциональным указанием порта (`:port`).
- **ПОЧЕМУ НЕ ИНАЧЕ:** Использование тяжелых моделей NLP для PII/DLP на локальной машине замедляет сетевой поток и увеличивает latency потока токенов; предвычисленные регулярные выражения работают с околонулевой задержкой (< 1 мс на запрос).

### 2.3 Автоматическое повышение статуса секрета (Promotion Flow)
- **ПОЧЕМУ:** Автоматически обнаруженные секреты (`auto_secrets`) требуют верификации оператором безопасности для перманентного закрепления, корректировки псевдонимов и назначения читаемых описаний.
- **ДЛЯ ЧЕГО:** Разделение динамического оперативного кэша от подтвержденной базы политик маскирования предприятия.
- **КАК:** Реализован HTTP-эндпоинт `POST /api/vault/promote`, который в единой транзакции переносит запись из `auto_secrets` в `secrets`, обновляя индекс маскирования `VaultStore`.
- **ПОЧЕМУ НЕ ИНАЧЕ:** Прямое автоматическое добавление в постоянные секреты без подтверждения засоряет базу ложными срабатываниями регулярных выражений и лишает администратора контроля над словарем псевдонимов.

### 2.4 Независимая фиксация транзакций ошибок upstream LLM
- **ПОЧЕМУ:** При возникновении сетевых сбоев, исчерпании квот (429) или ошибках авторизации upstream модели (401 Unauthorized) важно сохранять факт отправки запроса и объем потенциально раскрытых данных.
- **ДЛЯ ЧЕГО:** Полный аудит безопасности и расследование инцидентов утечек даже в условиях недоступности целевых API.
- **КАК:** В обработчиках маршрутов Fastify (`proxy/server.ts`) блок `finally` или обработка исключений гарантированно вызывает `vaultStore.logTransaction(...)` с фактическим статусом ответа upstream-сервиса.
- **ПОЧЕМУ НЕ ИНАЧЕ:** Логирование только успешных (200 OK) ответов скрывает вредоносные или ошибочные запросы, блокируемые на стороне LLM-провайдера.
